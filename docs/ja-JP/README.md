# ECC (Everything Claude Code)

AIエージェントはコードを書くことができますが、ECCはそれに統括されたエンジニアリングシステムとツールボックスを与えます：構築前に計画を立て、テストで変更を検証し、新たなコンテキストから自らの作業をレビューし、重要な知見を記憶し、繰り返しの成功を再利用可能なスキルやワークフローへと昇華させます。

```text
plan -> test -> implement -> review -> verify -> remember -> improve
（計画 -> テスト -> 実装 -> レビュー -> 検証 -> 記憶 -> 改善）
```

プロンプトのたびにそのプロセスを再構築する代わりに、一度インストールするだけでエージェントの作業基盤として定着します。

> コンテキストウィンドウを最適化し、それ以外のすべてを永続化する。

ECCはMITライセンスのオープンソースです。現在はClaude Codeで最も快適に動作し、Codexの公式同期パスを備えているほか、Cursor、OpenCode、Gemini、Zed、GitHub Copilot、Antigravity、Qwenなどの各種ハーネス向けのアダプターも提供しています。機能の対応状況については、[プラットフォームサポート一覧](#プラットフォームサポート) をご確認ください。

68のエージェント、292のスキル、94のレガシーコマンドシムに加え、フック、ルール、メモリ、継続的学習、およびAgentShieldセキュリティスキャンが利用可能です。各エージェントは計画、レビュー、ビルド修復、セキュリティ、アーキテクチャ、特定ドメイン業務に特化しています。

| 含まれる要素 | 数量 | 提供機能 |
| :--- | ---: | :--- |
| **エージェント** | 68 エージェント | 計画、レビュー、ビルド修復、セキュリティ、アーキテクチャ、専門ドメイン業務 |
| **スキル** | 292 スキル | TDD、調査、セキュリティ、ドキュメント、フロントエンド、データ、ML、運用など |
| **コマンド** | 94 コマンド | スキル優先サーフェスへの移行期における便利なエントリーポイント |
| **フック &amp; メモリ** | ランタイム | ガイドライン強制、セッション要約、継続的学習、インスティンクト、コンテキスト制御 |
| **ルール** | 選択可能 | 言語やプロジェクトに応じて選択する常時読み込み標準規格 |
| **AgentShield** | 同梱 | プロンプト、フック、MCP設定、権限、シークレット、エージェント定義のスキャン |

## ECCのインストール

> [!IMPORTANT]
> ECC 2.2には、Claude Code、Codex、Kimi Code向けの対話型ガイド付きセットアップパッケージが含まれています。
> ユニバーサルパッケージの実行にはNode.js 18以上が必要です。また、ClaudeプラグインのセットアップにはGitおよび`PATH`上のClaude Code 2.1以上が必要です。

### 推奨：ユニバーサル・ガイド付きセットアップ

Claude Codeプラグインのセットアップ、更新、スコープ変更、フックプロファイル変更を行う場合：

```bash
npx ecc-universal@2.2.1 setup
```

npmでバージョンやキャッシュのエラーが発生した場合は、再試行前にレジストリのバージョンを確認してください：

```bash
npm view ecc-universal version
```

ECC 2.2は主要な各種パッケージランナー経由でのガイド付きセットアップに対応しています：

| パッケージランナー | ガイド付きセットアップコマンド |
|---|---|
| npm / npx | `npx ecc-universal@2.2.1 setup` |
| pnpm | `pnpm dlx ecc-universal@2.2.1 setup` |
| Yarn 2+ | `yarn dlx ecc-universal@2.2.1 setup` |
| Bun | `bunx ecc-universal@2.2.1 setup` |

上記の例では、本リポジトリのリリースバージョンと一致する [公開済みECC 2.2.1リリース](https://www.npmjs.com/package/ecc-universal/v/2.2.1) を指定しています。バージョン固定はセキュリティ監査や整合性検証の代替にはなりません。パッケージコードを実行する前にリリースソースとレジストリの整合性を確認してください。未リリースの変更にはレビュー済みのチェックアウトを使用してください。

Yarn Classic 1には `yarn dlx` がありません。`npx` を使用するか、パッケージをグローバルインストールするか、一時的な実行のためにYarnをアップグレードしてください。

セットアップウィザードは変更を加える前に公式マーケットプレイスと既存のネイティブClaudeインストールスコープを調査し、選択したスコープに対して安全に `ecc@ecc` をインストール、更新、または移行します。ECCの更新、スコープ変更、フックプロファイル変更を行いたいときは、いつでも同じコマンドを再実行してください。このセットアップウィザードは現在Claude Codeプラグインを設定します。CodexまたはKimi Codeの場合は下記のマルチハーネスウィザードを使用してください。

一度の確認フローで複数のコーディングエージェントを設定するには、マルチハーネスウィザードを使用します：

```bash
npx ecc-universal@2.2.1 install --guided
```

Claude Code、Codex、Kimi Codeを任意の組み合わせで選択でき、書き込み前に各インストールチャネルと配置先を表示して検証し、最終確認を求めます。

| ハーネス | ガイド付きインストールの動作 |
|---|---|
| Claude Code | `user`、`project`、または `local` スコープのネイティブ `ecc@ecc` プラグインとECCフックプロファイルを設定 |
| Codex | ネイティブCodexマーケットプレイス/プラグインライフサイクル。フックのレビューと信頼決定はCodex側で管理 |
| Kimi Code | `./.kimi-code` 配下の管理対象プロジェクトファイル。ECCフック、モデル/プロバイダ設定、認証は構成されません |

自動化環境では、プロバイダ固有の選択を明示的に指定してください：

```bash
npx ecc-universal@2.2.1 install --guided \
  --harness claude --harness codex --harness kimi \
  --claude-scope local --claude-hooks standard \
  --profile core --yes
```

実際の書き込みを行わずに、ネイティブガイド付きCodexパスと管理対象Kimiパスをドライランで確認：

```bash
npx ecc-universal@2.2.1 install --guided --harness codex --dry-run
npx ecc-universal@2.2.1 install --profile core --target kimi --dry-run
```

2.2のエイリアス経由で以下の追加コマンドも利用できます：

```bash
npx ecc-universal@2.2.1 consult "security reviews" --target claude
npx ecc-universal@2.2.1 install --profile minimal --target claude --with capability:machine-learning
npx ecc-universal@2.2.1 doctor --target kimi
```

※ `npx ecc-install --profile minimal --target claude` は実行しないでください。`ecc-install` は `ecc-universal` 内のバイナリ名であり、個別に公開されたnpmパッケージではありません。

また、ECCは `cursor`、`antigravity`、`gemini`、`opencode`、`codebuddy`、`joycode`、`qwen`、`zed`、`hermes`、`openclaw` 向けの上級管理アダプターも同梱しています。これらのターゲットは、各アダプターがガイド付きの競合検出、更新、修復、アンインストールのライフサイクルマトリクスを通過するまで、ドキュメント記載の `ecc install --target ...` パスを使用します。いずれのウィザードも、検出されたすべてのハーネスへ勝手にインストールすることはありません。

### ハーネスごとに1つのパスのみを選択してください

Claude Code、Codex、その他のハーネスを同一マシン上で併用可能です。各ハーネスに対してインストール方法を1つだけ選択してください：

- **推奨デフォルト:** 上記のガイド付きClaudeプラグインセットアップを実行
- **Claude Codeでサポートされている別手法:** [ネイティブプラグインコマンド](#claude-codeの詳細) を使用
- **リリース2.2で利用可能:** Claude Code、Codex、Kimi Code向けのガイド付きパッケージセットアップ
- **推奨組み合わせ:** Claude Codeプラグイン + Codexネイティブプラグイン
- **推奨組み合わせ:** Claude Codeプラグイン + レガシーCodex同期フロー
- **避けるべき構成:** Claude Codeプラグイン + Claude完全手動インストール
- **避けるべき構成:** Codex同期 + Codexマーケットプレイスプラグイン

**インストール手法を重ねて実行しないでください。** 同一ハーネスにECCを重複してインストールすると、スキル、コマンド、フック、設定が二重に登録される恐れがあります。別々のハーネスに1回ずつインストールする場合は問題ありません。

もし既に複数のインストール手法を重ねてしまい重複が発生している場合は、直ちに [ECCのリセット / アンインストール](#eccのリセット--アンインストール) を参照してください。

**インストール時のトラブル？** 簡易な [インストール・実行時問題報告フォーム](https://github.com/affaan-m/ECC/issues/new?template=install-problem.yml) を開くか、`ecc feedback` を実行してください。ECCが診断情報を自動送信することは決してありません。

### Claude Codeの詳細

あるいは、Claude Code内で直接Claude Codeのネイティブプラグインコマンドを実行することもできます：

```text
/plugin marketplace add https://github.com/affaan-m/ECC
/plugin install ecc@ecc
```

このネイティブパスにより、ECCのスキル、エージェント、コマンド、およびプラグイン管理のフックがインストールされます。この方法を選んだ場合はここで完了してください。重ねてClaude Codeへの完全手動インストールを実行しないでください。

マーケットプレイス、プラグイン、競合スコープが既に存在する場合のエラーを含め、これらの組み込みコマンドの処理はClaude Codeが管轄しています。ECCはそのパーサーを横取りできません。どちらかのネイティブコマンドで既存のインストールやスコープ競合が報告された場合は、2.2のガイド付きセットアップを使用するか、競合するClaudeプラグインスコープを解決してから再試行してください。手動インストールを重ねないでください。

ECCインストール後、`/ecc:configure-ecc` を実行するとClaude内から安全な再構成スキルを呼び出せます。これは同じ安全なセットアップフローに委譲されますが、プラグインインストール後にのみ利用可能であり、初回インストール時にClaude Code組み込みの `/plugin` コマンドの代わりになるものではありません。

Claude Codeプラグインは `rules` を自動配布できないため、実際に必要なルールパックのみを追加してください：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
mkdir -p ~/.claude/rules/ecc
cp -R rules/common ~/.claude/rules/ecc/
cp -R rules/typescript ~/.claude/rules/ecc/  # ご利用のスタックに合わせて変更
```

まずは `rules/common` と、実際に使用する言語・フレームワークパック1つから始めることを推奨します。プラグインをインストールした場合は、その後に `./install.sh --profile full` を実行しないでください。

<details>
<summary><strong>settings.json を直接編集する場合（宣言的マーケットプレイス追加）</strong></summary>

`~/.claude/settings.json` に直接追加します：

```json
{
  "extraKnownMarketplaces": {
    "ecc": {
      "source": {
        "source": "github",
        "repo": "affaan-m/ECC"
      }
    }
  },
  "enabledPlugins": {
    "ecc@ecc": true
  }
}
```

これにより、上記の2つの `/plugin` コマンドと同じ結果が得られます。
</details>

<details>
<summary><strong>名称および移行に関する注意事項 (ecc@ecc, affaan-m/ECC, ecc-universal)</strong></summary>

ECCには3つの公式識別子があり、それぞれ用途が異なります：

- GitHubソースリポジトリ: `affaan-m/ECC`
- Claudeマーケットプレイス / プラグイン識別子: `ecc@ecc`
- npmパッケージ: `ecc-universal`

これは設計上の意図によるものです。Anthropicのマーケットプレイス/プラグインのインストールは正規プラグイン識別子によってキー指定されるため、ECCではツール名やスラッシュコマンドの名前空間を厳格なDesktop/APIバリデータに収まるよう短く保つ目的で `ecc@ecc` を使用しています。過去の投稿には以前の長いマーケットプレイス識別子が記載されている場合がありますが、レガシーエイリアスとして扱ってください。また、npmパッケージは `ecc-universal` の名称を維持しているため、npm経由のインストールとマーケットプレイス経由のインストールでは意図的に異なる名前が使用されます。

npmのリリースはコミットごとではなくバージョンダグごとに作成されるため、`ecc-universal` は `main` への毎回のプッシュではなく正式リリース（2.1, 2.2, ...）を追跡します。最新の開発版が必要な場合はGitからインストールしてください。

ローカルのClaude設定が初期化またはリセットされた場合でも、再購入等は一切不要です。まずは `node scripts/ecc.js list-installed` を実行し、続いて `node scripts/ecc.js doctor` と `node scripts/ecc.js repair` を実行してください。通常、これだけで環境を一から作り直すことなくECC管理ファイルを復元できます。
</details>

### Codex App および CLI

最新のCodexリリースでは、ECCをネイティブのリポジトリマーケットプレイスプラグインとしてインストールできます。マーケットプレイスエントリはリポジトリルートを使用するため、Codexのキャッシュにはマニフェストと参照されるすべてのスキル、MCP設定、フックランタイム、スクリプト、アセットが一緒に取得されます：

```bash
codex plugin marketplace add affaan-m/ECC
codex plugin add ecc@ecc
codex plugin list --json
node scripts/codex/check-plugin-cache.js
```

どちらの追加コマンドも冪等です。後から更新する場合は、`codex plugin marketplace upgrade ecc` に続けて `codex plugin add ecc@ecc` を実行してください。Codexは有効なプラグイン状態を有効な `CODEX_HOME` 内に1つだけ保持し、Claudeのような `user`、`project`、`local` スコープは提供しません。ネイティブフックには明示的な信頼設定が必要であり、Claudeの4つのECCフックプロファイルは使用されません。Codex内では、プロバイダ認識型のガイド付きフローのために `$configure-ecc` を呼び出してください。

過去の `scripts/sync-ecc-to-codex.sh` パスは、`~/.codex` 内に設定をコピー・マージする必要があるユーザー向けの下位互換オプションです。ネイティブプラグインを使用する場合は不要です。新しい同期スクリプトは所有権マニフェストを記録するため、クリーンアップ時にユーザー変更ファイルを保護できます。`~/.codex/config.toml` が生成されるよう、事前にCodexを1回起動してから実行してください：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
npm install
bash scripts/sync-ecc-to-codex.sh
```

Codexの会話やネイティブプラグインのキャッシュに触れることなく、このレガシー層を検査・削除する場合：

```bash
node scripts/ecc.js uninstall --legacy-codex-sync --dry-run
node scripts/ecc.js uninstall --legacy-codex-sync
```

マニフェスト導入前の古いインストールは安全第一で処理されます。ECCは目印の付いた `AGENTS.md` ブロックを削除しますが、自身が所有していると証明できないコピーファイルは保持し、確認用に報告します。

また、プロジェクトローカルなセットアップとして、ECCリポジトリをCodexで直接開くこともできます。Codexはグローバル同期なしでルートの `AGENTS.md` と `.codex/` 内の信頼されたプロジェクト設定を読み込みます。同期フローの上にネイティブマーケットプレイスプラグインを重複して追加しないでください。

リポジトリナビゲーション、サーフェス所有権、PR diffパケットのガイダンスについては、[Codex ECCナビゲーションマップ](../../docs/CODEX-NAVIGATION-GUIDE.md) を参照してください。ネイティブライフサイクルの詳細については [.codexプラグインノート](../../.codex-plugin/README.md) を参照してください。

## 高度なインストールオプション

<details>
<summary><strong>フックランタイムなしの低コンテキストインストール</strong></summary>

### 低コンテキスト / フックレスパス

ランタイムフックを使用せず、ECCのルール、エージェント、コマンド、プラットフォーム設定、コアワークフローのみを利用したい場合：

```bash
npx ecc-universal@2.2.1 install --profile minimal --target claude
```

ソースチェックアウトからの同等コマンド：

```bash
./install.sh --profile minimal --target claude
```

Windows環境：

```powershell
.\install.ps1 --profile minimal --target claude
```

このプロファイルでは意図的に `hooks-runtime` が除外されます。

手動Claudeインストールでは、Claude Codeが検出できるよう各スキルが `~/.claude/skills/<skill-name>/`（`claude-project` の場合は `.claude/skills/<skill-name>/`）に直接配置されます。過去のECC手動インストールをアップグレードする際、インストーラーはECCのインストール状態に記録されたネストされた `skills/ecc/` ファイルのみを移行します。フラットなスキルディレクトリがユーザー所有である場合、ECCはそれを保護し、競合警告を出力し、安全なアンインストールのために古い管理対象コピーを追跡して、ユーザーファイルを上書きしないようにします。

フックを無効化した通常のコアプロファイルの場合：

```bash
./install.sh --profile core --without baseline:hooks --target claude
./install.sh --profile core --no-hooks --target claude
```

後からフックランタイムを追加したい場合のみ実行：

```bash
./install.sh --target claude --modules hooks-runtime --enable-hooks
```

プロファイルやモジュールによってフックランタイムが具現化されるインストールには、明示的な決定が必要です。`--enable-hooks` または `--no-hooks` が指定されていない場合、インストーラーはフックが実行可能な内容を表示し、書き込みを行う前に停止します。ガイド付きインストーラー（`ecc install --guided`）では対話形式で確認されます。
</details>

<details>
<summary><strong>必要なコンポーネントのみを選択してインストール</strong></summary>

### 適切なコンポーネントを事前に検索

同梱のアドバイザーに問い合わせて、作業に合致するコンポーネントを確認できます：

```bash
node scripts/ecc.js consult "security reviews" --target claude
```

一致するコンポーネント、関連プロファイル、プレビュー/インストール用コマンドが返されます。実際のファイル配置計画を確認したい場合は、インストール前にプレビューコマンドを使用してください。

特定のスキルや機能を明示的にインストールすることも可能です：

```bash
./install.sh --target claude --skills tdd-workflow,security-review
node scripts/ecc.js install --profile minimal --target claude --with capability:machine-learning
```

コンポーネントごとの手動コピーも機能します。各コンポーネントは完全に独立しています：

```bash
# エージェントのみ
cp agents/*.md ~/.claude/agents/

# ルールディレクトリ（共通 + 言語別）
mkdir -p ~/.claude/rules/ecc
cp -r rules/common ~/.claude/rules/ecc/
cp -r rules/typescript ~/.claude/rules/ecc/   # 使用スタックを選択

# コア/汎用スキルのみ（Claude Codeは ~/.claude/skills の直下からスキルを読み込みます。~/.claude/skills/ecc/ にネストさせないでください）
mkdir -p ~/.claude/skills
cp -r .agents/skills/* ~/.claude/skills/
cp -r skills/search-first ~/.claude/skills/

# オプション: 移行期間中のスラッシュコマンド互換性維持
mkdir -p ~/.claude/commands
cp commands/*.md ~/.claude/commands/
```

廃止されたシムは `legacy-command-shims/` に保管されています。`/tdd` などの以前の名称がどうしても必要な場合のみ、そこから個別のファイルをコピーしてください。
</details>

<details>
<summary><strong>グローバルルールではなくプロジェクトローカルなルールを使用</strong></summary>

すべてのClaude Codeセッションではなく、特定のリポジトリのみにECCの基準を適用したい場合：

```bash
cd your-project
mkdir -p .claude/rules/ecc
cp -R /path/to/ECC/rules/common .claude/rules/ecc/
cp -R /path/to/ECC/rules/typescript .claude/rules/ecc/
```

ルールは常時読み込みされるコンテキストとなるため、まずは `common` と、実際に使用するスタック用のパック1つから始めてください。ルールを手動コピーする場合は、相対参照が機能しファイル名が衝突しないよう、ディレクトリ内のファイル単体ではなく言語ディレクトリ全体（例：`rules/common` や `rules/golang`）をコピーしてください。
</details>

<details>
<summary><strong>完全手動でのClaudeインストール</strong></summary>

プラグインパスを意図的に使用しない場合のみ利用してください：

```bash
git clone https://github.com/affaan-m/ECC.git
cd ECC
./install.sh --profile full
```

Windows環境：

```powershell
git clone https://github.com/affaan-m/ECC.git
cd ECC
.\install.ps1 --profile full
```

このパスを選んだ場合はここで完了してください。`/plugin install` を重ねて実行しないでください。

手動で厳選してインストールする場合、Claudeは `~/.claude/skills/` の直下からスキルを検出します。`~/.claude/skills/ecc/` のようにネストさせないでください。

#### フックのインストール

リポジトリ内の未加工の `hooks/hooks.json` を `~/.claude/settings.json` や `~/.claude/hooks/hooks.json` にそのままコピーしないでください。そのファイルはプラグイン/リポジトリ向けの設定です。フックコマンドのパスが正しく解決・書き換えられるよう、インストーラーを使用してください：

```bash
bash ./install.sh --target claude --modules hooks-runtime --enable-hooks
```

これにより、フックスクリプトが `~/.claude/` 配下にインストールされ、解決されたフックエントリが `~/.claude/settings.json` に登録されます。既存のユーザー設定やフックは保護されます。ECCが管理するエントリは安全な更新とアンインストールのために安定IDで追跡されます。

`/plugin install` 経由でECCをインストールした場合、それらのフックを `settings.json` にコピーしないでください。Claude Code v2.1+ はプラグインの `hooks/hooks.json` を自動的に読み込むため、`settings.json` で重複させると二重実行やOS間の競合が発生します。

Windows環境では、Claudeの設定ルートは `%USERPROFILE%\.claude` です。フックランタイムのインストール：

```powershell
pwsh -File .\install.ps1 --target claude --modules hooks-runtime --enable-hooks
```

#### MCPの設定

Claudeプラグインインストールでは、厳格なサードパーティゲートウェイでの過度に長いツール名を防ぎつつ、手動MCPセットアップの自由度を保つため、ECCにバンドルされたMCPサーバー定義を意図的に自動有効化しません。

実行中のClaude Codeサーバー変更には、Claude Codeの `/mcp` コマンドまたはCLI管理のMCPセットアップを使用してください。設定は `~/.claude.json` に保存されます。リポジトリ固有のMCPアクセスの場合は、`mcp-configs/mcp-servers.json` から必要な定義をプロジェクトスコープの `.mcp.json` にコピーしてください。

ECCがデフォルトで同梱するコネクターは1つのみ（`chrome-devtools`）です。それ以外はCLI/REST APIをラップしたスキルか、オプトイン方式のカタログエントリです。この設計方針および過去のデフォルトを整理した2026年6月の監査については [docs/MCP-CONNECTOR-POLICY.md](../../docs/MCP-CONNECTOR-POLICY.md) を参照してください。

既に独自にECC同梱のMCPを実行している場合は、以下を設定してください：

```bash
export ECC_DISABLED_MCPS="chrome-devtools"
```

ECCのインストールおよびCodex同期フローは、重複追加を行わずにそれらの同梱サーバーをスキップまたは削除します。`ECC_DISABLED_MCPS` はECCのインストール/同期用フィルタであり、実行中のClaude Codeの動的トグルではありません。

**重要:** `YOUR_*_HERE` プレースホルダーは実際のAPIキーに置き換えてください。
</details>

<details>
<summary><strong>マルチモデルコマンドの追加セットアップ</strong></summary>

`multi-*` コマンドは基本プラグイン/ルールインストールには**含まれていません**。

`/multi-plan`、`/multi-execute`、`/multi-backend`、`/multi-frontend`、`/multi-workflow` を使用するには、`ccg-workflow` ランタイムの追加インストールが必要です。[公式CCGインストールガイド](https://github.com/fengshao1227/ccg-workflow#readme) を確認の上、バージョンを選択してインストール・初期化してください。ECCはCCGをバンドルしておらず、監査済みCCGリリースを保証するものではありません。

このランタイムは、これらのコマンドが必要とする以下の外部依存関係を提供します：

- `~/.claude/bin/codeagent-wrapper`
- `~/.claude/.ccg/prompts/*`

`ccg-workflow` がない場合、これらの `multi-*` コマンドは正常に動作しません。
</details>

<summary><strong>リセット、修復、またはアンインストール</strong></summary>

### ECCのリセット / アンインストール

ユニバーサルパッケージからインストールした場合は、インストール時と同じプロジェクトディレクトリから実行してください：

```bash
npx ecc-universal@2.2.1 list-installed
npx ecc-universal@2.2.1 doctor
npx ecc-universal@2.2.1 repair
npx ecc-universal@2.2.1 uninstall --dry-run
npx ecc-universal@2.2.1 uninstall
```

ソースチェックアウトからは、再インストール前に管理状態を検査します：

```bash
node scripts/ecc.js list-installed
node scripts/ecc.js doctor
node scripts/ecc.js repair
node scripts/ecc.js uninstall --dry-run
```

ソースチェックアウトからの直接アンインストール：

```bash
node scripts/uninstall.js --dry-run
node scripts/uninstall.js
```

利用を終了する場合、アンインストールコマンドは任意の [20秒フィードバックフォーム](https://github.com/affaan-m/ECC/issues/new?template=quick-feedback.yml) を表示します。これは公開GitHub Issueであり、アンインストールを妨げることはなく、診断データを勝手に送信することもありません。また、いつでも `ecc feedback` を実行して問題報告や機能要望ルートを確認できます。

プラグインユーザーは、Claude Codeからプラグインを削除した後、手動でコピーして不要になったルールフォルダのみを削除してください。ECCはインストール状態に記録されたファイルのみを削除し、ハーネスディレクトリ内の無関係なファイルを侵害することはありません。

複数のインストール手法を重ねてしまった場合は、以下の順序で整理してください：

1. Claude Codeプラグインを削除。
2. 管理対象のインストール状態が含まれるプロジェクトディレクトリからECCアンインストールコマンドを実行。
3. 手動コピーして不要になったルールフォルダを削除。
4. 単一のパスで一度だけ再インストール。
</details>

## ECCの利用開始

カタログ全体を一気に使おうとせず、必要なワークフローから始めてください。

| 行いたい作業 | ここから開始 |
|---|---|
| 機能開発 | `/ecc:plan "機能の概要"` を実行後、`tdd-workflow` |
| バグ修正 | 失敗するテストで再現させた後、`tdd-workflow` |
| 新規コードのレビュー | 新しいコンテキストから `/code-review` |
| ビルド修復 | `/build-fix` |
| コードベースの整理 | `/refactor-clean` |
| コンテキスト使用量の確認 | `/context-budget` |
| 長時間のセッション終了 | `/save-session` または `/learn-eval` |
| セッションの再開 | `/resume-session` |
| エージェント設定の監査 | レビュー済みスキャナによる `/security-scan`、または `agentshield scan --path .` |

<details>
<summary><strong>プラグインコマンドと手動コマンド</strong></summary>

Claude Codeプラグインコマンドは名前空間付きの形式を使用します：


手動インストールでは、互換性のための短い形式が利用可能な場合があります：


<details>
<summary><strong>どのおすすめエージェントを使うべきか？</strong></summary>

スキルが正規のワークフローサーフェスですが、コマンド主導の運用のためにスラッシュコマンドも引き続き提供されています。

| 目的 | 利用サーフェス | 使用エージェント |
|---|---|---|

## セルフホストモデルとカスタムエンドポイント

ECCは各ハーネスの標準設定を通じて動作するため、公式プロバイダ、互換カスタムAPIエンドポイントやモデルゲートウェイ、あるいはセルフホストされたモデルを、ECCのワークフローを変えることなく利用できます。

Claude Codeの場合、ECCはAnthropicがホストするトランスポート設定をハードコードしていません。最小限のゲートウェイ設定例：

```bash
export ANTHROPIC_BASE_URL=https://your-gateway.example.com
export ANTHROPIC_AUTH_TOKEN=your-token
claude
```

ゲートウェイ側でモデル名のリマッピングを行う場合は、ECC側ではなくClaude Code側で設定してください。`claude` CLIが動作している状態であれば、ECCのフック、スキル、コマンド、ルールはモデルプロバイダに依存しません。Anthropicの [LLMゲートウェイドキュメント](https://docs.anthropic.com/en/docs/claude-code/llm-gateway) および [モデル設定ドキュメント](https://docs.anthropic.com/en/docs/claude-code/model-config) を参照してください。

別個のコンピュートおよびサービング環境を用意することで、そのゲートウェイの背後で任意のオープンソースモデルを実行・セルフホストできます。GPUリソースが必要な場合、[Itô](https://compute.itomarkets.com) はECCの推奨コンピュートスポンサーですが、任意のGPUプロバイダを利用可能です。スポンサーシップリンクは受動的なものであり、RFQの発行、容量予約、コンピュートのプロビジョニング、サービング構成を勝手に行うことはありません。一方、`ecc ito find` は明示的に設定された正規のItô CLIを呼び出し、認証済みのライブRFQを送信します（容量の予約は行いません）。Itôを通じたマネージド推論は現在準備中です。

### Itô コンピュート CLI ブリッジ

`ecc ito` は別途インストールされた正規のItôクライアントに処理を委譲します。ECCは自前で二次的なAPIクライアントを維持しません。`ecc ito login [--no-browser]` はデバイス認証を実行し、デフォルトでItô検証ページを開いてmacOS Keychainにデバイストークンを保存します（`--no-browser` でページ遷移を抑制可能）。ECC自体はブラウザ自動化を行いません。`ecc ito auth` は検証専用であり、`--no-browser` を受け付けません。利用可能な操作は `ecc ito login`、`ecc ito auth`、`ecc ito find`、`ecc ito status`、および別途ゲートされた `ecc ito evals` です。対応するMCPツールは `ito_auth`、`ito_find`、`ito_status` です。`ito_auth` は既存の認証情報を検証し、ノードの適格性確認はCLI専用です。

`ito-compute-cli` パッケージは現在未公開です。Itôランタイムリポジトリ（デスク強化中のため非公開、デザインパートナーに提供）の `cli/ito-compute-cli` 配下でローカルビルドし、`npm ci` と `npm run check` を実行後、`ECC_ITO_CLI_EXECUTABLE` にそのビルドの絶対パス `dist/bin/ito.js` を設定してください。ログイン時に `ITO_API_KEY` は継承されません。認証、検索、ステータス確認は設定時に `ITO_API_KEY` を直接転送し、`ITO_AUTH_MODE=legacy` は不要です。`ecc ito logout` は現在のデバイス認証情報を取り消し、リモートでの取り消しが確認できない場合はローカルコピーを保持します。デバイストークンはデフォルトでmacOS Keychainを使用します。ファイルフォールバックを使用する場合は所有者のみのディレクトリ/ファイル権限を保持する必要があります。ECCはこの認証情報を持つクライアントを `PATH` から自動検出することはありません。完全なRFQ権限およびMCPセットアップ規約については [`ito-compute` スキル](../../skills/ito-compute/SKILL.md) を参照してください。

`find` は認証済みのライブRFQを送信します（容量の予約は行いません）。`evals` には `ITO_ENABLE_SIXTYTWO_LIVE=1` と `--live-sixtytwo`、別途インストールされた `sixtytwo-cli==0.3.33`、明示的なノードリスト、既存の絶対設定ディレクトリのすべてが必要です。レンタル、起動、復旧、修復、購入は行えません。ECCは見積もりロック、購入、ワークロード、推論パスを公開せず、見つからないクライアントや失敗したライブ呼び出しをローカルの結果で代用することは決してありません。

## 主要な概念

<details>
<summary><strong>エージェント、スキル、フック、ルールの詳細</strong></summary>

### エージェント

サブエージェントはスコープが限定された委譲タスクを自律的に処理します。例：

```markdown
---
name: code-reviewer
description: コードの品質、セキュリティ、保守性をレビューします
tools: Read, Grep, Glob, Bash
model: opus
---

あなたはシニアコードレビュアーです...
```

### スキル

スキルは主要なワークフローサーフェスです。直接呼び出したり、エージェントが自動的に提案・再利用したりできます。移行期間中は `commands/` も保守されていますが、新しいワークフローの開発はまず `skills/` に追加されます。

```markdown
# TDD ワークフロー

1. 先にインターフェースを定義する
2. 失敗するテストを書く (RED)
3. 最小限の実装コードを書く (GREEN)
4. リファクタリングを行う (IMPROVE)
5. 80%以上のカバレッジを検証する
```

### フック

ツールの実行イベントに応じてフックが発火します。例：`console.log` の残存を警告するフック：

```json
{
  "matcher": "tool == \"Edit\" && tool_input.file_path matches \"\\\\.(ts|tsx|js|jsx)$\"",
  "hooks": [{
    "type": "command",
    "command": "#!/bin/bash\ngrep -n 'console\\.log' \"$file_path\" && echo '[Hook] console.log を削除してください' >&2"
  }]
}
```

### ルール

ルールは常時遵守すべきガイドラインであり、`common/`（言語非依存）と言語別のディレクトリに整理されています：

```
rules/
  common/          # 普遍的な原則（常にインストール）
  typescript/      # TS/JS固有のパターンとツール
  python/          # Python固有のパターンとツール
  golang/          # Go固有のパターンとツール
  swift/           # Swift固有のパターンとツール
  php/             # PHP固有のパターンとツール
  arkts/           # HarmonyOS / ArkTSの制約とパターン
```

構造とインストールの詳細は [`rules/README.md`](../../rules/README.md) を参照してください。
</details>

## なぜECCを選ぶのか？

| システム化されていない環境 | ECCを導入した環境 |
| :--- | :--- |
| 計画がチャット履歴の奥深くに埋もれて消える | 実装開始前に編集可能なアーティファクトとして計画が具現化される |
| 「TDDで書いて」と頼んでもモデルが忘れがち | RED -> GREEN -> REFACTOR のエビデンス付きワークフローが強制される |
| 同じコンテキストがコードを書き、自己レビューも行う | 新鮮な別コンテキストのレビュアーがデグレや盲点を客観的に検証する |
| メモリとは膨大なチャットログを延々と保存すること | セッションが要約、インスティンクト、再利用可能なスキルへと蒸留される |
| 品質の担保が人間の声かけ頼みになる | フックがプロンプトの外側で決定論的な品質チェックを強制する |
| エージェントの設定が無条件に信頼されてしまう | AgentShieldがハーネス自体を攻撃対象サーフェスとして監査する |

### TDD: テスト駆動開発

```text
/ecc:plan "従量課金アラート機能の追加"
  -> 計画を確認または編集
  -> tdd-workflow スキルをアクティブ化
  -> 実装前に失敗テスト（RED）のエビデンスを取得
  -> テストが通過する（GREEN）まで実装
  -> 新しいコンテキストからコードレビューを実施
  -> 指摘事項を回帰テストと共に対処
  -> ビルド、リント、型、テストの完全通過を検証
```

単に動くコードだけでなく、「計画、失敗テスト、成功テスト、レビューの指摘、最終検証」という一連のエビデンスの軌跡が残ります。

### スキルによるコンテキストの最適化

ルール、スキル、エージェント、フックはそれぞれ異なる役割を果たします。これらの責任を分離することで、セッションごとにリポジトリ全体を丸ごと投入することなく、必要な能力のみを追加できます。

| 概念 | 役割 | コンテキスト上の挙動 |
|---|---|---|
| **スキル** | TDD、セキュリティレビュー、調査などの再利用可能なワークフロー | タスクで必要になった際にオンデマンドで読み込まれる |
| **エージェント** | 独自のコンテキストとツール権限を持つスコープ限定の作業者 | 計画、実装、レビューを互いに隔離する |
| **ルール** | プロジェクトや言語の永続的なコーディング基準 | 常に読み込まれるため、選択的にインストールする |
| **フック** | ハーネスイベントによってトリガーされるスクリプト | モデルのコンテキスト外部で実行される |
| **インスティンクト** | 実際のセッションから確信度スコア付きで学習されたパターン | 関連性が高い場合にのみ想起される |

### 異なるハーネス間でのコンテキスト共有

ECCのメモリ保管庫（Memory Vault）により、Claude、Codex、Hermes、OpenClaw、Kimiなどの各種ハーネス間で、共通の可読なローカルMarkdown形式を用いて永続コンテキストやハンドオフを共有できます。プロジェクトおよびチームメモリは `.ecc/memory/`、ユーザーメモリは `~/.ecc/memory/` に保存されます。

スキル単体、最小構成、手動、Claudeプラグインインストールでは、Memory Vaultランタイムが `PATH` に配置されません。CLIやオプションのMCPサーバーを使用する前に、npmランタイムを別途インストールしてください：

```bash
npm install -g ecc-universal@2.2.1
ecc memory init --scope project
ecc memory search "認証の移行" --target-harness codex
ecc memory doctor
```

メモリは未監査のコンテキスト情報であり、実行可能なポリシーではありません。重要な主張は信頼できる公式ソースと照合し、合意された知識は管理されたプロジェクトドキュメントへと昇格させてください。オプションの `ecc-memory-mcp` サーバーは、デフォルトで有効化されることなく、安全な保存・検索・読み取り・doctorサーフェスを提供します。

[統合メモリワークフローを開く →](../../skills/unified-memory/SKILL.md)

<details>
<summary><strong>Memory Vault の詳細：スコープ、ハンドオフ、信頼境界</strong></summary>

Memory Vaultは、ベンダー固有のログをコピーしたりエージェント間でプロンプトをやり取りしたりする代わりに、ポータブルな `ecc.memory.v1` Markdownドキュメントを保存します。プロジェクトメモリは誤コミットを防ぐ `.gitignore` で保護されます。チームスコープは、人間が内容を確認してバージョン管理に含める共有用途にのみ使用してください。

ランタイムのインストール後、CLIとMCPエントリポイントが利用可能か確認します：

```bash
ecc memory --help
command -v ecc-memory-mcp
```

```bash
# プロジェクト保管庫を初期化
ecc memory init --scope project

# ハンドオフ内容をファイルに書き出し、対象のハーネスを指定
ecc memory handoff \
  --from hermes \
  --target codex \
  --title "認証移行の継続作業" \
  --body-file ./handoff.md

# 別のハーネスからそれを想起
ecc memory search "認証移行" --target-harness codex
ecc memory read <memory-id>

# チームメモリを共有する前に保管庫を検証
ecc memory doctor
```

メモリ本文はコマンドライン引数として直接渡すのではなく、`--stdin` または `--body-file` 経由でのみ受け付けられます。検索結果にはアクティブなプロジェクトおよびチームメモリが返されます。ユーザースコープの検索は明示的な要求が必要です。エージェントは想起された内容を実行可能な指示やポリシーとして扱ってはならず、必ず公式情報と照合する必要があります。

MCPアクセスを利用する場合は、[`mcp-configs/mcp-servers.json`](../../mcp-configs/mcp-servers.json) の `ecc-memory-vault` エントリを必要なハーネスに追加し、`ecc-memory-mcp` を起動します。サーバーは小文字の `ECC_MEMORY_HARNESS` 識別子で起動する必要があります。ユーザースコープの利用には `ECC_MEMORY_ALLOW_USER_SCOPE=1` の明示設定が必要です。ワークフローと信頼境界については [`skills/unified-memory/SKILL.md`](../../skills/unified-memory/SKILL.md) を、詳細設計は [`docs/design/ecc-memory-vault.md`](../../docs/design/ecc-memory-vault.md) を参照してください。
</details>

## プラットフォームサポート

ECCのコアNode.js CLIおよびインストーラーは **Windows、macOS、Linux** で動作しますが、一部のオプション機能には環境ごとの差異があります。一部の継続的学習、GAN、オーケストレーションパスはBashやPythonを必要とし、ハーネスごとにフック、エージェント、スキルのAPIも異なります。

| プラットフォーム | ステータス | 現在の制限事項 |
|---|---|---|
| **Linux** | コアサポート | 一部のオプション機能でBash、Python、プロバイダ固有のツールが必要 |
| **macOS** | コアサポート | スタンドアロンGANシェルパスがシステム標準のBash 3.2と非互換であり、スコア解析の既知問題があります（[#2674](https://github.com/affaan-m/ECC/issues/2674)） |
| **Windows + WSL** | コアサポート | WSL環境はLinuxに準拠。Windowsホスト側との統合はハーネスに依存 |
| **Windows ネイティブ** | 制限付きサポート | 継続的学習v2のオブザーバーデーモンおよびメモリ書き込みにWindows固有の既知問題があります（[#2489](https://github.com/affaan-m/ECC/issues/2489), [#2626](https://github.com/affaan-m/ECC/issues/2626)）。シェル依存のオプション機能にはGit BashやWSLが必要、または利用不可 |

以下の `安定版`、`ベータ版`、`実験的`、`指示レイヤーのみ` は機能性のステートメントです：

| ハーネス | ステータス | 推奨配布形態 | 重要な制限事項 |
|---|---|---|---|
| **Claude Code** | 安定版（プライマリ） | プラグインまたは選択的インストーラー | プラグインは全カタログをモデルに提示するため、コンテキストを重視する場合は選択的プロファイルを推奨。シェル依存のスキルは一部OSで非互換 |
| **Codex** | ネイティブプラグイン対応 | Codexマーケットプレイスプラグインまたはリポジトリ設定 | ネイティブフックには明示的な信頼設定が必要で、Claudeのフックプロファイルは非対応。旧同期は互換用のみ |
| **Cursor** | ベータ版（プロジェクトアダプター） | `.cursor/` への選択的インストール | エージェント検出はCursorビルドに依存。フックセットに一部差異あり（[#2419](https://github.com/affaan-m/ECC/issues/2419)） |
| **OpenCode** | ベータ版（ビルドプラグイン） | ビルド後に選択的インストール | カタログのサブセットを提供。プロバイダとモデルはOpenCode側で指定（[#2617](https://github.com/affaan-m/ECC/issues/2617)） |
| **GitHub Copilot** | 指示レイヤーのみ | リポジトリ同梱の指示およびプロンプトファイル | フック、ランタイムエージェント、自動委譲、ネイティブスキル検出は非対応 |
| **Gemini, Zed, Antigravity, Qwen, Hermes, OpenClaw, Kimi, CodeBuddy, JoyCode** | 実験的 / 最小アダプター | ハーネス固有の選択的ターゲット | ファイル配置と指示のポータビリティはテスト済み。Claudeと同等の完全機能は保証されません |

<details>
<summary><strong>パッケージマネージャの自動検出</strong></summary>

プラグインは以下の優先順位で使用中のパッケージマネージャ（npm, pnpm, yarn, bun）を自動検出します：

1. **環境変数**: `CLAUDE_PACKAGE_MANAGER`
2. **プロジェクト設定**: `.claude/package-manager.json`
3. **package.json**: `packageManager` フィールド
4. **ロックファイル**: package-lock.json, yarn.lock, pnpm-lock.yaml, bun.lockb から判定
5. **グローバル設定**: `~/.claude/package-manager.json`
6. **フォールバック**: 利用可能な最初のパッケージマネージャ

優先パッケージマネージャの設定方法：

```bash
# 環境変数による指定
export CLAUDE_PACKAGE_MANAGER=pnpm

# グローバル設定による指定
node scripts/setup-package-manager.js --global pnpm

# プロジェクト設定による指定
node scripts/setup-package-manager.js --project bun

# 現在の設定を検出・確認
node scripts/setup-package-manager.js --detect
```

または `/setup-pm` コマンドを使用してください。
</details>

<details>
<summary><strong>フックランタイム制御（環境変数）</strong></summary>

環境変数フラグを使用して、厳格性の調整や特定フックの一時無効化が可能です：

```bash
# フックの厳格性プロファイル (デフォルト: standard)
export ECC_HOOK_PROFILE=standard

# 無効化するフックID（カンマ区切り）
export ECC_DISABLED_HOOKS="pre:bash:tmux-reminder,post:edit:typecheck"

# SessionStartの追加コンテキスト文字数上限 (デフォルト: 8000文字)
export ECC_SESSION_START_MAX_CHARS=4000

# 低コンテキスト環境向けにSessionStartの追加コンテキストを完全に無効化
export ECC_SESSION_START_CONTEXT=off

# セッション一時ファイルの保持日数 (デフォルト: 30日)
# 0, off, false, disabled, never, none でプルーニングを無効化
export ECC_SESSION_RETENTION_DAYS=14

# SessionStartがコンテキストに注入するインスティンクトの最大数 (デフォルト: 6)
export ECC_MAX_INJECTED_INSTINCTS=6

# 注入に必要なインスティンクトの最低確信度 (0〜1, デフォルト: 0.7)
export ECC_INSTINCT_CONFIDENCE_THRESHOLD=0.7

# 確信度＋スタック関連度によるランク付け (デフォルト: on)
export ECC_INSTINCT_RELEVANCE_RANKING=on

# コンテキスト/スコープ警告は維持し、APIレート費用試算警告のみ抑制
export ECC_CONTEXT_MONITOR_COST_WARNINGS=off
```

Windows PowerShellでの設定例：

```powershell
[Environment]::SetEnvironmentVariable('ECC_CONTEXT_MONITOR_COST_WARNINGS', 'off', 'User')
[Environment]::SetEnvironmentVariable('ECC_SESSION_RETENTION_DAYS', '14', 'User')
```
</details>

<summary><strong>エージェントデータホーム（マルチハーネス分離）</strong></summary>


詳細は [affaan-m/ECC#2065](https://github.com/affaan-m/ECC/issues/2065) を参照してください。

## トークン最適化

エージェント利用はトークン消費を管理しないと高額になる場合があります。以下の設定により、品質を維持したままコストを大幅に抑制できます。完全ガイド: [docs/token-optimization.md](../../docs/token-optimization.md)。

<details>
<summary><strong>推奨設定</strong></summary>

`~/.claude/settings.json` に追加：

```json
{
  "model": "sonnet",
  "env": {
    "MAX_THINKING_TOKENS": "10000",
    "CLAUDE_AUTOCOMPACT_PCT_OVERRIDE": "50",
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku"
  }
}
```

| 設定項目 | デフォルト | 推奨値 | 効果 |
|---|---|---|---|
| `model` | opus | **sonnet** | 約60%のコスト削減。コーディング作業の80%以上に対応 |
| `MAX_THINKING_TOKENS` | 31,999 | **10,000** | リクエストごとの潜在的な思考コストを約70%削減 |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | 95 | **50** | より早い段階でコンパクションを行い、長期セッションでの品質を維持 |
| `ECC_CONTEXT_MONITOR_COST_WARNINGS` | on | **定額制ユーザーは off** | コンテキスト枯渇警告は残しつつ、APIレートの試算警告を非表示化 |

高度なアーキテクチャ推論が必要な場合のみOpusに切り替えます：
```
/model opus
```
</details>

<details>
<summary><strong>日常ワークフローコマンド</strong></summary>

| コマンド | 利用タイミング |
|---|---|
| `/model sonnet` | 通常のほとんどの作業におけるデフォルト |
| `/model opus` | 複雑なアーキテクチャ設計、デバッグ、高度な推論 |
| `/clear` | 無関係なタスクへ切り替える際（完全かつ無料のリセット） |
| `/compact` | タスクの論理的な節目（調査完了時、マイルストーン達成時） |
| `/cost` | セッション中のトークン消費状況を確認 |
</details>

<details>
<summary><strong>戦略的コンパクション</strong></summary>

`strategic-compact` スキルは、コンテキスト使用率95%での自動コンパクションに依存するのではなく、論理的な節目での `/compact` を提案します。

**コンパクションすべきタイミング:**
- 調査や探索が完了し、実装に着手する直前
- マイルストーンが完了し、次の作業を開始する直前
- デバッグが完了し、機能開発を再開する前
- アプローチが失敗し、新しい手法を試みる前

**コンパクションを避けるべきタイミング:**
- 実装の真っ最中（変数名、ファイルパス、途中経過の状態が失われるため）
</details>

<details>
<summary><strong>コンテキストウィンドウの管理</strong></summary>

**重要:** すべてのMCPを一度に有効化しないでください。各MCPツールの説明文が200kのコンテキスト枠を消費し、実質70k程度まで圧迫されることがあります。

- 1プロジェクトあたり有効にするMCPは10個未満を推奨
- アクティブなツール総数を80個未満に維持
- 未使用のMCPサーバーは `/mcp` で無効化（`~/.claude.json` に保持）
- コンテキストが圧迫された場合は `/context-budget` を実行し、不要なルールを削除
</details>

## 動作要件

<details>
<summary><strong>Claude Code CLIバージョンとフック自動読み込みの仕様</strong></summary>

### Claude Code CLIのバージョン

**最低要件: v2.1.0 以上。** プラグインシステムにおけるフック処理の仕様変更に伴い、Claude Code CLI v2.1.0以上が必要です。

バージョンの確認：
```bash
claude --version
```

### 重要：フックの自動読み込み動作

> WARNING: **コントリビューター向け注意:** `.claude-plugin/plugin.json` に `"hooks"` フィールドを追加しないでください。これは回帰テストによって厳格にチェックされています。

Claude Code v2.1+ は、インストールされたプラグイン内の `hooks/hooks.json` を規約に基づき**自動的に読み込みます**。`plugin.json` 内で明示的に宣言すると、重複検出エラーが発生します：

```
Duplicate hooks file detected: ./hooks/hooks.json resolves to already-loaded file
```
</details>

## トラブルシューティング

<details>
<summary><strong>ECCが二重に表示される / フックが2回実行される</strong></summary>

主な原因は、Claudeプラグインをインストールした後に `./install.sh --profile full` などを重ねて実行したことです。

1. Claude Codeプラグインをアンインストール。
2. ECCのチェックアウトディレクトリから `node scripts/ecc.js uninstall --dry-run` を実行。
3. 手動コピーして不要になったルールフォルダを削除。
4. 単一の手法で一度だけ再インストール。

フック固有の確認事項は [hooks README](../../hooks/README.md) を参照してください。
</details>

<details>
<summary><strong>フックが動かない / "Duplicate hooks file" エラーが出る</strong></summary>

**`.claude-plugin/plugin.json` に `"hooks"` フィールドを追加しないでください。** Claude Code v2.1+ はインストールされたプラグインから `hooks/hooks.json` を自動的に読み込みます。明示的な宣言は重複検出エラーの原因になります。
</details>

<details>
<summary><strong>Codexマーケットプレイスは入るがスキルが読み込まれない</strong></summary>

ECCチェックアウトからキャッシュチェックを実行してください：

```bash
node scripts/codex/check-plugin-cache.js
```

未解決の親参照が報告された場合は、`codex plugin marketplace upgrade ecc` でキャッシュを更新し、再度 `codex plugin add ecc@ecc` を実行してCodexを再起動してください。
</details>

その他のFAQは [TROUBLESHOOTING.md](../../TROUBLESHOOTING.md) および [docs/TROUBLESHOOTING.md](../../docs/TROUBLESHOOTING.md) を参照してください。
