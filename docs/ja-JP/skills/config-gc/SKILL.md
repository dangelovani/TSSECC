# Config GC — Claude Code環境のガベージコレクション

ランタイムのガベージコレクション（GC）に着想を得た手法です。参照されなくなったオブジェクト、重複、期限切れ、低価値な項目を定期的にスキャンし、容量とコンテキストを解放します。最大の原則は、**「削除には必ず人間が介在すること（Human-in-the-loop）。自律的に勝手な削除を行わないこと」** です。

## 発動タイミング

- ユーザーがClaude Code設定の整理、監査、またはスリム化を求めた場合
- スキルが多すぎる、フックの出力がうるさい、セッションの起動が遅いといった不満が出た場合
- 月次または定期的な設定見直しの時期が到来した場合
- 大規模なスキルパック（本リポジトリなど）をインストールした後、既存設定との重複を解消したい場合

※ プロジェクトソースコードの整理（それはリファクタリングです）、チャット履歴のクリア、Claude Code自体のアンインストールには使用しないでください。

## 設計哲学

1. **追記専用の設定は漏洩・肥大化する:** スキル、メモリ、フック、権限は追加ばかりされがちです。定期的な見直しがなければ静かに陳腐化します。
2. **一度きりの大量粛清より、定期的な小規模監査:** 約30日ごとにスキャンし、毎回少量の候補を提示します。
3. **チャネル別の選別戦略:** スキル、フック、権限など、蓄積のタイプごとに陳腐化のシグナルは異なります。単一のルールを一律に適用してはなりません。
4. **ソフトデリート（論理削除）を最優先:** `.disabled` へのリネーム ＞ `~/.claude/_gc_trash/` への移動 ＞ 完全削除。常にアンドゥ（復元）パスを残します。
5. **人間の1件ごとの確認を強制:** すべての候補に対して `[y/n/skip]` の確認を行います。「すべてはい」のショートカットは提供しません。
6. **ログの永続記録:** すべてのGC実行結果を `~/.claude/gc_log.md` に追記します（何を、なぜ変更したか、どうやって元に戻すか）。

## スキャンチャネル

| # | チャネル | 対象パス | 陳腐化 / 冗長性のシグナル |
|---|---|---|---|
| 1 | **スキル** | `~/.claude/skills/*/` | 名称の大幅な重複、最近のセッションで一度も発動していない、実際の業務ドメインとの乖離、破損または空のSKILL.md |
| 2 | **メモリ** | `~/.claude/**/memory/*.md` + インデックス | 1つのトピックに複数のインデックスエントリ、新しい内容と矛盾する記述、過去の日付、インデックスから漏れた孤立ファイル、統合すべき100単語未満の断片 |
| 3 | **フック** | `~/.claude/hooks/` + 設定 | ディスク上に存在するがどのフック設定からも参照されていないスクリプト、書き直しにより不要になった旧バージョン |
| 4 | **権限** | `settings.json` の `permissions.allow` | 重複エントリ、ワイルドカードで既に包含されている個別エントリ（例：`Bash(*)` があるのに `Bash(git push)` が残っている）、過去の実験による一時的な許可 |
| 5 | **MCPサーバー** | `~/.claude.json` または `.mcp.json` | 接続に失敗するサーバー、機能的な重複、長期間未使用 |
| 6 | **定期リマインダー/ジョブ** | 各種設定箇所 | 30日以上前の1回限りジョブ、対象スクリプトが既に存在しないジョブ |
| 7 | **プロジェクト履歴** | `~/.claude/projects/*/` | 陳腐化したハンドオフスナップショット、新しい状態に置き換わった古いセッション記録 |
| 8 | **ランタイムキャッシュ** | `cache/`, `file-history/`, `logs/`, `shell-snapshots/` | サイズと更新日時でソートし、30日以上前かつ大容量のものを候補とする |

## ワークフロー

1. **スキャン:** 全チャネル（またはユーザー指定のチャネル）を走査。候補ごとに「パス、チャネル、検出理由、サイズ、最終更新日時」を収集。
2. **ランク付け:** 確信度順（破損/孤立 = 高、単に古い = 低）に並べ、番号付きテーブルとして提示。1回の実行あたり最大20件程度に抑えます（網羅ではなく定期実行が目的）。
3. **1件ずつの確認:** 各候補についてエビデンスを示し、`[y/n/skip]` を確認。ユーザーはいつでも中断可能。
4. **承認項目のソフトデリート:** スキルやフックは `.disabled` へのリネーム、ファイルは `_gc_trash/<日付>/` への移動を優先。権限エントリ（JSON）は設定ファイルをバックアップし、削除項目を `gc_log.md` にそのまま記録した上で `jq` で除外。完全削除はユーザーの明示要求時のみ。
5. **ログ記録:** `~/.claude/gc_log.md` にタイムスタンプ、処理項目、復元手順を記録。
6. **レポート:** 回収できた容量、健全なチャネル、次回推奨レビュー日を報告。

## スキャン用コマンド例

孤立したフックスクリプトの検出（チャネル3）:
```bash
for f in ~/.claude/hooks/*; do
  name=$(basename "$f")
  grep -rq "$name" ~/.claude/settings.json ~/.claude/settings.local.json 2>/dev/null \
    || echo "ORPHAN: $f"
done
```

冗長な権限エントリの検出（チャネル4）:
```bash
jq -r '.permissions.allow[]' ~/.claude/settings.local.json | sort | uniq -d
if jq -e '.permissions.allow | index("Bash(*)")' ~/.claude/settings.local.json >/dev/null; then
  jq -r '.permissions.allow[]' ~/.claude/settings.local.json \
    | grep '^Bash(' | grep -vF 'Bash(*)'
fi
```

復元可能なソフトデリート:
```bash
gc_date=$(date +%Y-%m-%d)
mkdir -p ~/.claude/_gc_trash/$gc_date
mv ~/.claude/skills/dead-skill ~/.claude/_gc_trash/$gc_date/
echo "$(date -Iseconds) moved skills/dead-skill -> _gc_trash/$gc_date/ (undo: mv back)" >> ~/.claude/gc_log.md
```

## アンチパターン

- **一括承認（バルク処理）:** 「15件すべて削除しますか？ [y/n]」と尋ねるのは設計思想に反します。1項目ごとに1つの判断を求めます。
- **初回パスでの完全削除:** `_gc_trash/` への退避や `.disabled` リネームを行わない即座の完全削除は誤りです。
- **「古い」＝「不要」と決めつけること:** 60日間触られていないスキルでも、確定申告や四半期決算など季節性の業務である可能性があります。経過期間は判断材料の1つに過ぎず、だからこそ人間の確認が必要です。
- **内容を読まずにメモリを切り捨てること:** 矛盾する2つのメモリファイルを整理する際は、両方を精読して最新の真実を残す必要があり、単に長い方を消すようなことはしてはなりません。
- **`~/.claude`（またはプロジェクトの `.claude/`）の外側に触れること:** Config GCがプロジェクトのソースツリーを勝手にいじることは絶対にありません。

## 関連スキル

- `skill-stocktake` — スキルの「品質」を監査（config-gcはスキルの「存在」を監査）。GCを生き残ったスキルに対してstocktakeを実行します。
- `workspace-surface-audit` — 追加側の監査（何をインストールすべきか）。config-gcはその対となる削減側の機能です。
- `configure-ecc` — スキルインストール後、既存環境との重複を解消するためにconfig-gcを実行します。
- `continuous-learning` — 本スキルが後に監査するメモリファイルを生成します。
- `security-review` — 権限チャネルの監査と密接に連携します。
