# Itô 推論サービング (Itô Inference)

`ito-inference` は、Itôコンピュート上での推論サービングを扱う唯一の正規ECCスキルです。`ito-serve` という名称のリクエストもここにルーティングされます（2つ目の `ito-serve` スキルを作成・インストールしないでください）。ECCはノードへのSSH接続、重みファイルのダウンロード、推論エンジンの起動、エンドポイントの公開、予約や支払いの実行を勝手に行うことは決してありません。

## 現在の本番環境境界（Current Production Boundary）

現在、マネージドサービングは提供されていません。ECCブリッジは `login`、`auth`、`find`、`status`、および明示的にゲートされた `evals` のみを公開しています。`serve` サブコマンドは存在しません。正規ランタイムは `inference` を未サポートの互換性プローブとしてのみドキュメント化しており、ECCはそれを呼び出したり依存したりしません。MCPサーフェスは認証、検索、ステータスのみを公開しています。局所的に強制される保証として、ECCは認証情報を持つ正規クライアントを解決・生成する前に `serve` を拒否します。

したがって、認証やコマンドの実行を行う前に停止してください。機能が存在しない旨を報告し、呼び出し元のエージェントに制御を戻してください。ローカルのランナー、SSHヘルパー、ブラウザワークフロー、購入エンドポイント、あるいは未追跡のローカルな `ito-serve` ドラフト等で勝手に代用してはなりません。

## 必要な利用資格（Required Entitlement）

サービング機能が実装された際の最初のゲートは、「サーバー側で検証済みの完了した予約」です。ハーネスのメモリ、RFQ、見積もり、ノードIP、SSHアクセスなどは、利用資格のエビデンスにはなりません。バックエンドが、認証されたアカウント、予約、GPUトポロジー、リージョン、ファブリック、期間、モデルポリシーに紐づいた最新のサービング適格性を返却する必要があります。期限切れ、取り消し済み、不一致、不完全、または解放済みの予約は、確認を行う前にフェイルクローズ（安全側に倒して拒否）されます。

## 将来のCLIおよびAPI規約

予定されているコマンド名は `serve` です（`inference` は本番規約の確立後に明示的に非推奨化された互換エイリアスとしてのみ残る可能性があります）。将来の引き渡しは以下と同等でなければなりません：

```sh
ecc ito serve \
  --booking <サーバー検証済み予約ID> \
  --manifest <レビュー済みの絶対パスJSONファイル> \
  --confirmation-ref <非認可の不透明な確認参照ID> \
  --idempotency-key <安定した再試行キー> \
  --json
```

レビュー済みマニフェストには、モデルのリビジョン、エンジンとバージョン、量子化、テンソル/パイプラインのトポロジー、エンドポイント公開ポリシー、成果物のチェックサム、ストレージ上限、ランタイム制限、任意のTTFT/TPOT目標、最大追加コストを明記する必要があります。生のAPIキー、SSHキー、ノードのパスワード、ベアラートークンを引数、マニフェスト、ログ、MCP結果、チャットに含めてはなりません。

クライアントはマニフェストのパスを正規化し、シンボリックリンクを拒否し、リンクを追従せずに通常ファイルを開き、適切な所有権と制限されたアクセス権を要求し、サイズ上限を強制し、開かれたファイルディスクリプタからバイト列をハッシュ化しなければなりません。そのダイジェストハッシュは、ワークロードの変更を行う前に、確認情報にバインドされたダイジェストと完全に一致しなければなりません。パスのすり替え、ダイジェスト不一致、サイズ超過、変更可能な危険なファイルは、すべてフェイルクローズされます。

ECCではなく正規APIがワークロードの作成を管轄し、`ok`、`live_api_contacted`、`notice`、および `data` または `error` を含む構造化JSONを返却する必要があります。サービングデータには、安定した予約ID、ワークロードID、マニフェストID、冪等性キーID、および状態Enumを含める必要があります。ヘルスチェックとモデル検証に合格するまで、エンドポイントが稼働中であると主張してはなりません。エラーには、シークレットを含まない安定したエラーコードと安全なメッセージを含める必要があります。

## 確認および実行ゲート

ワークロードの作成前に、以下のすべてを必須とします：

1. 正規バックエンドからの最新の利用資格およびサービング適格性の確認。
2. レビュー可能で不変のマニフェストと決定論的なダイジェストハッシュ。
3. 短い有効期限とリプレイ防止機能を備えた、アカウント、アクション、マニフェスト、コストに紐づく個別の1回限り確認。CLI引数は不透明で単独では認可力を持たない確認参照IDのみを渡し、サーバーがアウトオブバンドでベアラー機能を解決・消費します。
4. ワークロードとアトミックに予約される、呼び出し元提供の冪等性キー。
5. サーバー側でのファブリック、容量、モデルポリシー、ストレージ、コストの検証。

認証は「身元」の証明であり、「ワークロード作成の権限」ではありません。ログイン、APIキー、見積もり、完了した予約をもってサービング確認の代わりとすることはできません。検査や計画の生成によってワークロードを作成してはなりません。キャンセルやクリーンアップは、独自のスコープ付き確認と冪等性境界を持つ個別の変更操作です。

## ライフサイクルと復旧

正規クライアントがテナントスコープのステータス確認、ログ、メトリクス、キャンセル、クリーンアップ操作を公開するまで、本番サーフェスは未完成です。すべての操作に接続タイムアウトと全体タイムアウト、取り消しを認識するエラーハンドリング、構造化出力が必要です。曖昧なトランスポート障害が発生した場合は、再試行する前に冪等性キーでステータスを照会してください（単に応答が失われたという理由だけで2つ目のワークロードを作成してはなりません）。認証情報が取り消された場合はポーリングを停止し、自動的にログインを再試行することなく呼び出し元エージェントに制御を戻します。

エンドポイントの健全性、モデルの同一性、カナリア推論のすべてに合格した後にのみ `ready` を報告してください。中間状態や終端の失敗状態は正確に報告する必要があります。クリーンアップは観測可能でなければならず、基盤となる予約を解放または変更してはなりません（その個別の経済的アクションが明示的に認可されている場合を除く）。

## 提案されているバックエンドステージ

以下のステージはECC内のコードではなく、将来のバックエンドの動作を示したものです：

1. 利用資格、トポロジー、ファブリック、コストの各ゲートを検証。
2. チェックサムで固定された重みをバックエンド管理のストレージに取得。
3. レビュー可能なトポロジー/エンジン計画を出力および検証。
4. プロバイダのコントロールプレーン経由で起動（ECCからの直接のルートSSHは絶対に行わない）。
5. ウォームアップ、健全性とモデル同一性のテスト、SLOカナリアの実行を経て、エンドポイントとマスキング済み設定を登録。

上記のすべてのゲートおよびライフサイクル操作が正規ランタイムに実装されるまで、本スキルはフェイルクローズな利用可能性チェックおよびドキュメント引き渡しにとどまります。
