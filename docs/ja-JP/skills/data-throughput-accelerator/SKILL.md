# データスループットアクセラレータ (Data Throughput Accelerator)

大量のデータ移動、変換、保存がボトルネックになっている場合に本スキルを使用します。目的は単なる実行速度の向上だけではありません。エビデンス（証明）を伴って、正当なデータをより高速に正しい宛先へ届けることがゴールです。

## 最初に切り分けるべき項目

最適化に着手する前に、以下の各要素を明確に分離します：

- ソースからの抽出速度 (Source extraction speed)
- ネットワーク転送速度 (Network transfer speed)
- DWH/ストレージへのロード速度 (Warehouse/load speed)
- 変換処理速度 (Transform speed)
- 提供テーブルのデータ鮮度 (Serving-table freshness)
- ジョブ実行中に発生する最新データの増加ペース (Live tail growth)

パイプライン自体のスループットが高くても、追いつき完了時間よりも早く新規データが流入し続ける場合、システムは「遅延している」ように見えます。

## 高速化のためのヒューリスティクス

- **コンピュートをデータの存在する場所へ移動する:** データを移動させるのではなく、データがすでに存在する場所で計算を実行します。
- 大規模に配置されたファイルに対しては、DWHネイティブのスキャン、結合（Join）、追記（Append）を優先します。
- 処理済みのファイルやパーティションをスキップできるよう、マニフェストやチェックポイントを活用します。
- 読み取りおよび追記パターンに合致したパーティショニングとクラスタリングを適用します。
- 小さなファイル、リクエスト、書き込みは適切にバッチ化します。
- 一意キー、マニフェスト、または置き換え可能なステージングテーブルを活用し、書き込み処理を冪等（Idempotent）にします。
- 生データ（Raw）、派生データ（Derived）、提供用データ（Serving）の各テーブルを分離し、整合性検証を個別に行えるようにします。

## ワークフロー

1. 現在のソース、ターゲット、およびマニフェストの契約（スキーマ・規約）を精査する。
2. バックログ（未処理量）を測定する：外部ファイル数、マニフェスト行数、Raw行数、Derived行数、最小/最大タイムスタンプ、未処理件数。
3. 安全な追いつきテストまたはサンプルベンチマークを実行する。
4. バリアント間の比較検証：バッチサイズ、ワーカー数、DWH SQLの最適化、ファイルグループ化、ステージング構成、マニフェスト更新方式。
5. 件数とタイムスタンプの整合性が保たれる最も高速な手法のみを採用する。
6. その手法をCLIツール、定期ジョブ、ワークフロー定義、または運用手順書（Runbook）として体系化する。
7. 体系化された手法の実行後に、最終的な整合性検証（Accounting）を再実行する。

## 整合性検証サマリー（出力規約）

厳格な整合性ブロックを出力します：

```text
データスループット測定結果:
- 検出されたソースファイル数: 294
- 今回の実行で処理されたファイル数: 294
- 追加されたRawデータ行数: 9,683,598
- 追加されたDerivedデータ行数: 8,917,585
- 残余テール: 読み戻し時点で 24 ファイル
- 実行時間: 38.7秒
- 正当性検証ゲート: マニフェスト件数とテーブル最大タイムスタンプの一致を確認済み
```

## ガードレール

- 測定指標の見栄えを良くするために生データを削除してはなりません。
- 失敗したファイルを暗黙的にスキップしてはなりません。
- 過去のバックフィル進捗と最新データのリアルタイム鮮度を混同してはなりません。
- ターゲットテーブルとマニフェストの照合が一致するまで、パイプライン完了と判断してはなりません。
- 金融、医療、規制対象、または顧客に影響を与えるデータの場合、リプレイエビデンスと承認ゲートを必ず維持してください。
