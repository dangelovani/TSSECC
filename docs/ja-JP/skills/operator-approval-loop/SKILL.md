# Operator Approval Loop（運用者承認ループ）

外部取引先と対話するエージェントは、自己判断で勝手にメッセージを送信してはならず、社内向けに常に運用者へ状況を報告しなければなりません。このスキルはその契約（プロトコル）を定義します: すべての送信ドラフトは債務（obligation）として起草・登録され、運用者が正確なテキストを承認/却下し、配信台帳が何が送信されたかを証明します。

## 使用場面

- エージェントが共有チャンネル、メール、またはチャットにおいて顧客、サプライヤー、投資家、パートナーへの返信を起草し、送信前に人間の承認が必要なとき。
- 送信された各メッセージと、正確なドラフトテキスト、承認した運用者、および決定時刻を結びつける監査証跡が必要なとき。
- 古い承認によって書き直された最新ドラフトが誤って送信されたり、2つのワーカーが同じ承認済みメッセージを二重送信するのを防止したいとき。
- すでに台帳に記録されている事実を、ドラフトが取引先に何度も再質問してしまうのを防ぎたいとき。

## 動作の仕組み

### オブジェクトモデル

| オブジェクト | 意味 |
| --- | --- |
| Obligation（債務/タスク） | 取引先に対して果たすべき1つの義務。ステータスは `drafted`（起草済） → `approved`（承認）または `rejected`（却下） → `sent`（送信済）と遷移。`direction`, `counterparty`, `channel`, および `updated_at` エポックを保持。 |
| Draft（ドラフト） | 正確なドラフトテキスト、そのテキストのSHA-256ハッシュ、発生元座標（プラットフォーム、チャンネル、スレッド、ユーザー）、および優先度（P0〜P3）を保持するサイドカー行。Obligationごとに1つ存在し、再起票で置換。 |
| Decision（意思決定） | 運用者による承認または却下。運用者ID、ノンス、および決定対象のドラフトエポックとともに記録。 |
| Approval snapshot（承認スナップショット） | 認可された決定記録者によって記録された、不変のテキスト、ハッシュ、エポック、および宛先。スナップショットが欠落している場合、配信は許可されない。 |
| Claim（クレーム/ロック） | ランダムトークンと状態を持つ永続的予約。1つのObligationに対してアクティブなクレームは最大1つ。 |
| Delivery（配信記録） | 1つの (obligation, decision) ペアに対する1回の送信または通知を証明する台帳行。 |

参照スキーマは [references/approval-ledger.sql](references/approval-ledger.sql) にあります。

### ドラフトの起草・登録（Filing）

1. 入力のクレンジング。制御文字の除去、単一行フィールドの空白の圧縮、文字数制限（ドラフト本文、サマリー、コンテキスト、取引先名）の適用。空欄やサイズ超過のフィールドは無言で切り詰めるのではなく拒否します。
2. ベースラインゲートの実行（後述）。登録を拒否する場合があります。
3. ドラフトテキストのSHA-256ハッシュ化。承認パネルがどのテキストを承認しようとしているかを表示できるよう、ハッシュのプレフィックスをサマリーに含めます。
4. アップサート（挿入/更新）。同一の (counterparty, channel) に対して未解決の起草中Obligationがすでに存在する場合、ドラフトサイドカーを置き換え、Obligationの `updated_at` を進めます。この更新が**エポックローテーション**となります: 古いエポックをキーとする決定は、新しいテキストをリリースできなくなります。存在しない場合は、ステータス `drafted` で新しいObligationを挿入します。
5. 起票レシートは、設定および検証された社内運用（Ops）向け宛先にのみルーティングします。発生元がその社内宛先である場合は、そこで確認応答を返します。「沈黙しない（Never-silent）」とは社内への報告を意味し、外部への自動返信を意味しません。ドラフトハッシュ、承認ステータス、運用者ID、およびワークフローメタデータを、取引先に見えるチャンネルに漏らしてはなりません。

検証済みの社内宛先が利用できない場合、起票結果は社内ツールの結果または運用者向け画面にとどめます。外部または不明な発生元にフォールバックしてはなりません。部外者に公開されるツール結果は社内画面ではありません。

ドラフトの起草は外部への応答を許可するものではありません。ポリシーで許可された確認質問や中立的な応答は別の送信決定であり、`counterparty-channel-discipline` の制約に従います。

### ベースラインゲート（Baseline gate）

ドラフトが起草される前に、取引先に関する最新のベースライン情報（台帳、契約書ストア、CRM等）を照会します:

- 締結済みまたは納品済みの契約記録が存在する場合: 証拠と推奨事項を提示してドラフトの起草を拒否します。契約締結後に取引先に仕様を尋ねるような事態を防止するためのゲートです。
- 運用者によるオーバーライド: `force_despite_signed_contract` を指定すると起草が許可され、ドラフトコンテキストに `[BASELINE_OVERRIDE_SIGNED_CONTRACT]` のスタンプが付与されます。
- ゲートサービスに接続できない場合: 起草は続行され、コンテキストに `[BASELINE_CHECK_UNAVAILABLE]` のスタンプが付与されます（ガードが無効だったことがパネルに明示されます）。障害によってゲートが無言でバイパスされることはありません。
- 事実情報が取得できた場合は、最新の事実を `[BASELINE FACTS: ...]` ダイジェストとしてコンテキストに添付し、最新の真実に基づいたドラフトを作成します。

### 承認決定（Deciding）

承認パネルには、ステータスが `drafted` かつ方向が `we_owe_them` のObligationが一覧表示されます。承認または却下は、ドラフトのエポック（`draft_updated_ts`）を保持する決定行を書き込み、同一トランザクション内でObligationのステータスを変更します。現在の `updated_at` とエポックが一致しない決定は「期限切れ（stale）」とみなされ、何もリリースしてはなりません。

承認決定の場合、同じトランザクションで不変の `obligation_approval_snapshots` 行（決定およびObligation ID、現在のドラフトエポック、正確なテキストとSHA-256、プラットフォーム/チャンネル/スレッド、種別 `draft_sent`）が挿入されます。

### 配信（Delivering）

SQLiteリファレンスは [references/approval_claims.py](references/approval_claims.py) にあります。これはディスパッチの権限を付与しますが、トランスポート（実際の通信）自体は呼び出しません。

1. 承認済みドラフトの検出。検出は送信許可ではありません。`claim()` は独自の `BEGIN IMMEDIATE` トランザクションを開始し、スナップショットと照合して現在の承認エポック、正確なテキスト、計算されたSHA-256、および完全な宛先を検証し、一意のクレームを挿入してトークンを返します。競合が発生した場合はトランスポート前に停止します。
2. `begin_dispatch()` はバインディングを再検証し、トークンを使用して `claimed` から `dispatching` へアトミックに変更します。コミット後に正確な `draft_text` と宛先を受け取れるのは、勝ち残った呼び出し元のみです。テキストを再生成したり、送信のために変更可能なサイドカーを再読み込みしたり、別の試行にペイロードを使い回してはなりません。
3. 送信成功が確認されたら `complete()` を呼び出します。これにより配信座標がアトミックに記録され、クレームが配信済みにマークされ、Obligationが `sent` に変更されます。
4. 例外、タイムアウト、ワーカーのクラッシュ、またはレシート保存の失敗が発生した場合、試行はブロックされた状態になります。`mark_unknown()` で不確実性を記録します。未知のクレームは期限切れにならず、再オープンや自動リトライも行われません。

保証されるのは「承認決定ごとに1回の自動ディスパッチ試行」であり、「厳密に1回の外部配信（exactly-once delivery）」ではありません。

| クレームの状態 | 許可される次の状態 |
| --- | --- |
| claimed | dispatching または 送信前のキャンセル |
| dispatching | delivered または unknown |
| unknown | 信頼できる照合（reconciliation）経由でのみ delivered |
| delivered, cancelled | 終端状態。決定キーの再利用は不可 |

クレームがアクティブな間、データベースの保護機能によりObligation、ドラフト、決定の書き込み（置換を含む）が凍結されます。

### 時間制限付き自動承認（オプション）

ドラフトに `auto_send_after`（エポック秒）を保持させることができます。期限までに決定が下されなかったドラフトを定期スイープ処理が承認し、運用者 `auto-ttl` を記録して通常パスで配信を進めます。運用者の手動操作が常に優先されます。

### シグナル連携（Signal linkage）

ドラフトは回答対象となる受信Obligation（`signal_obligation_id`）を指定できます。これにより受信から起草までの遅延測定や、SLAスキャンにおける対応済み判定が可能になります。

## 具体例

### ドラフトの起草

```text
file_request(
  draft="Thanks, we can hold the slot until Friday. Which start date works?",
  counterparty="acme-supplier",
  context="reply to delivery window question",
  origin_platform="slack", origin_channel="#acme-shared",
  origin_thread="1712345678.000100", priority="P1",
  signal_obligation_id=412)
-> {obligation_id: 431, draft_sha256: "9f2c...", refiled: false}
```

設定された検証済みの社内運用宛先には次のように表示されます:  
`Draft filed for approval (P1, sha 9f2c8a1b). Waiting on operator.`  
取引先に見える発生元チャンネルには起票通知は送信されません。

### 修正指示による再起票

運用者がより短いドラフトを要求した場合、同じ (counterparty, channel) で再起票すると `refiled: true` が返され、ハッシュが更新され、`updated_at` が進みます。古い管理画面の行で承認ボタンが押されたとしても、古いエポックを持っているため無視されます。

### ゲートによる拒否

```text
DeskApprovalError: baseline gate refused this draft: the ledger shows a
signed contract for 'acme-supplier'. Evidence: master agreement executed
2026-08-14. Recommendation: do not ask. Re-file with
force_despite_signed_contract=true if this is genuinely a new thread.
```

## テストすべき不変条件（Invariants to test）

- 起票レシートは設定された検証済みの社内運用先のみに送信される。
- 同一の (counterparty, channel) を2回起票すると、1つのObligationと2つのエポックが生成される。
- 古いエポックを持つ決定が配信行を生み出すことは決してない。
- 2つの同時要求者は1つのディスパッチ権限のみを取得し、敗者はトランスポートを試行しない。
- 未知の結果やレシート保存の失敗によって自動リトライが有効化されることはない。
- 正常終了時は、同一トランザクション内でレシートと送信完了ステータスが記録される。
- アクティブなクレームが存在する間は再起票がブロックされる。
