# ベンチマーク最適化ループ (Benchmark Optimization Loop)

「20倍高速化してほしい」「50通りの再帰的最適化を試したい」といった要求を、システムを確実に改善できる境界付きの測定ループへと変換するために本スキルを使用します。

## 必須のベースライン

以下の要素が揃うまで最適化に着手してはなりません：

- 最適化対象の操作
- 常時グリーンを維持すべき正当性検証ゲート（テスト）
- 測定指標: 経過時間（Wall time）、p95レイテンシ、行数/秒、実行あたりコスト、メモリ消費量、エラー率
- 現在のベースライン測定値
- 探索予算: 最大試行バリアント数、制限時間、許容最大コスト、データへの影響上限

ユーザーから非現実的な目標が提示された場合でも、その意欲を受け止めつつ、ループを有界かつ測定可能な形に設計します。

## ループ手順

1. ベースラインを測定する。
2. エビデンスに基づいてボトルネックを特定する。
3. 1つの仮説ごとに1つのバリアント（変更案）を生成する。
4. 同一形状の入力データを用いて各バリアントを実行する。
5. 正当性、安全性、再現性に欠けるバリアントは却下する。
6. 最も高速で安全なバリアントを採用（プロモート）する。
7. 採用された手法をスクリプト、コマンド、テスト、設定ファイル、またはドキュメントに体系化する。
8. ベースラインと採用バリアントを再実行し、改善差分を確定確認する。

## バリアント管理表

以下のようにバリアントを記録・追跡します：

```text
バリアント | 仮説 | 実行コマンド | 測定時間 | 正当性 | 備考
baseline | 現行の実装 | npm run job | 120s | yes | 安定
batch-500 | ラウンドトリップの削減 | npm run job -- --batch 500 | 42s | yes | 採用
parallel-8 | ワーカー数の増強 | npm run job -- --workers 8 | 31s | no | レート制限発生
```

## 再帰的探索

再帰的最適化やハイパーパラメータ探索の場合：

- すべての実行結果を台帳（Ledger）に記録・永続化する。
- 直前の実行だけでなく、これまでに採用された最高バリアントと比較する。
- ホールドアウト検証またはリプレイ検証を維持する。
- 改善幅が測定誤差の範囲内になった場合、正当性テストに失敗した場合、コストが予算を超過した場合、または説明可能な範囲を超えて一度に多くの変数を変更し始めた場合は停止する。

探索空間を完全に網羅していない限り、「大域的最適（Global optimum）」ではなく「測定された最も安全な最善バリアント」と表現してください。

## 採用ゲート (Promotion Gate)

以下の条件をすべて満たすまで、新しいバリアントを本番デフォルトとして採用してはなりません：

- 正当性テストをすべて通過していること。
- パフォーマンス差分が再現されているか、理論的に説明されていること。
- ロールバック手順が自明であること。
- 変更内容がバージョン管理または永続的な運用手順書（Runbook）に記録されていること。
- 最終サマリーに正確な実行コマンドと測定値が含まれていること。
