# Inherit Legacy Style（レガシースタイルの継承）

コードベースをスキャンして4つのメタアーキテクチャ次元にわたる暗黙の規約を抽出し、競合をユーザーと1つずつ対話的に解決して、強制力のある `.ai-style-rules.md` に合意内容を結実させることで、レガシープロジェクトにおけるAIコードスタイルのドリフトを防止します。言語およびフレームワークに完全に中立です。

## 有効化のタイミング

- ユーザーが `/inherit-legacy-style` と入力したとき
- 既存の手書きレガシープロジェクトへのAIオンボーディングに言及したとき
- AIが生成するコードが既存のプロジェクト規約から「逸脱（ドリフト）」することを懸念しているとき
- プロジェクトの暗黙的なコーディングルールを抽出・成文化したいとき

## 使用場面

レガシープロジェクトのスタイルを維持し、AI生成によるスタイルのドリフトを防止する必要がある場合に使用します。トリガー条件は上記の **有効化のタイミング** を参照してください。

## 前提条件

- Git（推奨。非Gitプロジェクトの場合はインクリメンタルモードでファイルのタイムスタンプにフォールバックします）
- プロジェクトルートへの読み取り/書き込み権限（`.ai-style-rules.md` およびオプションで `CLAUDE.md` を生成します）

## ワークフロー

### ステップ 0 — モードの自動検出

プロジェクトルートにある `.ai-style-rules.md` の存在を暗黙的に確認します:

| ファイルが存在するか？ | モード |
|---|---|
| いいえ | **分岐 A — 初回フルスキャン** |
| はい | **分岐 B — インクリメンタルスニフ（差分検知）** |

モードを1行で宣言して続行します。ユーザーに選択を求めてはいけません。

### 分岐 A — 初回フルスキャン

**1. スケールの測定とスキャン階層の選択**

```bash
git ls-files | grep -cE '\.(js|ts|jsx|tsx|vue|py|go|rs|java|kt|rb|php|cs|swift|c|cpp|h)$'
```

| 階層 | ソースファイル数 | 戦略 |
|---|---|---|
| Small（小） | ≲ 50 | すべてのソースを精読 |
| Medium（中） | 50–500 | インフラ層は精読、ビジネス層は各次元ごとに2〜3件サンプリング |
| Large（大） | ≳ 500 | 厳格なサンプリング＋予算上限。まず `--stat` のサマリーを確認し、その後対象を絞って読み込み |

**2. 4つの次元に沿ったスキャン**

1. **ファイル構造（File Anatomy）** — ファイル内の宣言順序（インポート → 型定義 → メインロジック → ヘルパー → エクスポート）
2. **状態と制御フロー（State & Control Flow）** — 非同期状態、ページネーション、フラグなどの命名規則
3. **インフラストラクチャ（Infrastructure）** — 横断的ユーティリティ（インターセプター、フォーマッター、ミドルウェアなど）の配置場所
4. **エラーハンドリング（Error Handling）** — try/catch vs グローバルインターセプター vs Result型の返却、nullチェックの慣習

**3. シグナル閾値によるノイズ低減の適用**

ユーザーに質問（割り込み）する前に、シグナルの強度を評価します:

- **弱シグナル（Weak signal）** → 自動抑制: 少数派が5%未満 かつ 件数10件未満 → 多数派を採用し、少数派はDONT（禁止事項）へ追加
- **強シグナル（Strong signal）** → ユーザーへ確認（Grill）: ほぼ均等の分割、またはコア次元に関するセマンティックな分岐
- **小規模プロジェクトの例外**: ソース数が50件以下の場合、「3対2」は多数派とはみなされず、ユーザーへの確認対象となります

**4. 競合の順次解決（Grilling Protocol）**

強シグナルの競合ごとに、4つの選択肢を含む質問を厳密に**1つずつ**提示します:

> 根拠: `pathA` ではスタイルXが使用され、`pathB` ではスタイルYが使用されています
> 警告: リスク: 両方が混在するとプロジェクトのスタイルの一貫性が崩れます
> 選択: `1` Xに従う  `2` Yに従う  `3` これは進化・移行中でありルールを更新する  `4` 新しいルールを定義する

ユーザーが回答するまで一時停止し、回答後に次の競合に進みます。決して質問をまとめて提示してはいけません。

**5. 必須3セクションを含む `.ai-style-rules.md` の生成**:
- **[Golden Files（模範ファイル）]** — 何を示しているかの注釈付きの実ファイルパス
- **[Naming & State-Control Rules（命名および状態管理ルール）]** — 検証可能な具体的規約
- **[DONTs（禁止事項）]** — 伝播させてはならないアンチパターン

**6. 永続フックの導入**

強制力の強度をユーザーに尋ねます（`AskUserQuestion` を使用）:

| 選択肢 | メカニズム |
|---|---|
| **1** ソフトフック（推奨） | プロジェクトの `CLAUDE.md` に `@.ai-style-rules.md` の参照を記述 |
| **2** ハードフック | ソフトフックに加え、`settings.json` に `PreToolUse[Write\|Edit\|MultiEdit]` フックを設定 |
| **3** フックなし | ルールファイルのみ保持し、ユーザーが必要に応じて手動で参照 |

### 分岐 B — インクリメンタルスニフ

1. 既存の `.ai-style-rules.md` を読み込みます。コミットフィンガープリントがある場合、`git diff <last_hash> HEAD --stat` で差分を特定します
2. 最近のGit変更を確認します（`git log -3 --stat` → 疑わしいファイルをオンデマンドで精査）
3. 大規模なdiff（数百ファイル以上）の場合: `--stat` のサマリーのみ確認し、最大の変更箇所をサンプリング
4. 新しいコードを記録されたルールと比較 → 競合が見つかった場合は同様にGrilling Protocolで順次解決
5. `.ai-style-rules.md` の末尾に進化ログを追記（過去のルールを決して上書きしないこと）

### ターンごとの強制（Per-Turn Enforcement）

`.ai-style-rules.md` がコンテキストに読み込まれている場合（CLAUDE.md経由など）、すべてのコード記述タスクは思考チェーン内の**準拠宣言（compliance declaration）**で開始し、準拠する模範ファイルと回避するDONTsを明記しなければなりません。

## 仕組み

本スキルは `.ai-style-rules.md` の有無により初回実行か差分実行かを自動判定します:

- **初回（分岐 A）** — プロジェクト規模を測定し、4つのメタアーキテクチャ次元（ファイル構造、状態/制御フロー、インフラ、エラー処理）に沿ってスキャンし、シグナル閾値で微小な競合を排除し、強シグナルの競合をユーザーと順次解決して、模範ファイル・命名規則・禁止事項を含む `.ai-style-rules.md` を生成し、フックの導入を提案します。
- **インクリメンタル（分岐 B）** — 既存ルールを読み込み、最近のGit差分から新規パターンや競合を検査し、見つかった競合を対話プロトコルで解決して、既存ルールを壊さずに進化ログとして末尾に追記します。
- **ターンごとの遵守** — `CLAUDE.md` 経由でフックされている場合、すべてのコード生成タスクの冒頭で準拠宣言を行い、規約を確実に遵守します。

## 出力仕様

- プロジェクトルートの `.ai-style-rules.md`（ヘッダーにコミットフィンガープリントと規模階層を含む）
- オプションで `@.ai-style-rules.md` への参照を含む `CLAUDE.md`
- `### [YYYY-MM-DD] Style Evolution Log` として追記される進化ログ

## アンチパターン

- FAIL: 規模測定ステップを省略してはならない — 30ファイルのプロジェクトでサンプリングを行うと情報不足になり、5,000ファイルのプロジェクトをフルスキャンすると破綻します
- FAIL: 複数の競合質問を一度にまとめて提示してはならない — 確認は厳格に1問ずつ行います
- FAIL: インクリメンタルモードで既存ルールを上書きしてはならない — 常に進化ログとして追記します
- FAIL: ユーザーに確認せずに「ハードフック」をデフォルトにしてはならない — 強制強度はユーザーが選択します
- FAIL: 構文や技術スタックの良し悪しを判断してはならない — メタアーキテクチャの統一のみを扱います
- FAIL: 模範ファイルからバグまで真似てはならない — 構造のみを再利用し、欠陥は指摘します

## ベストプラクティス

- スキャンを開始する前に、検出されたモード（初回 vs インクリメンタル）と規模階層を1行で宣言する
- 大規模プロジェクトでは、まず `--stat` のサマリーを読み、その後疑わしいファイルに対してピンポイントで `Read` を行う
- シグナル閾値によってノイズを処理させる — 843対8のような命名の偏りは、ユーザーの手を煩わせずに自動解決する
- シグナル強度に迷った場合は、ユーザーへの質問を選択する
- 通常は CLAUDE.md のソフトフック（`@.ai-style-rules.md`）で十分であり、ハードフックは機械的な強制を望む場合にのみ適用する

## 関連スキル

- `init` — コードベースのドキュメントを含む新しいCLAUDE.mdを初期化
- `code-review` — 正確性とスタイルの問題についてdiffをレビュー
- `simplify` — コードの再利用と簡素化の機会をレビュー

## 具体例

1. **初回のオンボーディング**
   - ユーザー: 「この古いコードベースのスタイルを変えずに、AIをオンボーディングするのを手伝ってほしい」
   - アクション: 分岐Aのフルスキャンを実行 → 規模を測定 → 4つの次元をスキャン → 競合を順次解決 → `.ai-style-rules.md` を生成 → フック強度（ソフト/ハード/なし）を提案。

2. **チームの変更に伴うインクリメンタル更新**
   - ユーザー: 「新しいモジュールを追加した。既存のスタイルルールはそのまま維持したい」
   - アクション: 分岐Bのインクリメンタルスニフを実行 → Git差分を記録済みルールと比較 → 新たな競合を順次解決 → ルールを上書きせず進化ログを追記。

3. **CLAUDE.mdを通じたDONTs（禁止事項）の強制**
   - ユーザー: 「すべての新しいコードがプロジェクトのルールに確実に従うようにしたい」
   - アクション: ソフトフックを導入 → セッションごとに `.ai-style-rules.md` が自動ロード → 各コード記述タスクの冒頭で準拠宣言を行い、模範パターンを再利用しつつ禁止パターンを回避。
