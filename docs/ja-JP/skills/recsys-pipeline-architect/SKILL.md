# レコメンドシステム・パイプラインアーキテクト (recsys-pipeline-architect)

合成可能なレコメンデーション、ランキング、フィードパイプラインを設計・スキャフォールディングするためのスキルです。xAIのオープンソース [For You アルゴリズム](https://github.com/xai-org/x-algorithm) (Apache 2.0) で普及した **6段階パターン**（Source → Hydrator → Filter → Scorer → Selector → SideEffect）を体系化しています。本スキルは同パターンの独立した再実装（MITライセンス）であり、元のソースコードは一切コピーしていません。

アップストリーム: <https://github.com/mturac/recsys-pipeline-architect>

## 使用するタイミング

- ユーザーが「特定のユーザーやコンテキストに対して上位K件のアイテムを選定する」システムを構築したい場合
- 「Xをどうランク付けすべきか」という相談や、フィード/パーソナライズの課題に取り組む場合
- スコアリング関数は既に存在するが、その周辺のパイプライン構造が必要な場合
- 単一の関連度スコアから、重み調整可能な複数アクション予測モデルへ移行したい場合
- LLMやMLスコアラーをラップし、フィルター、ハイドレーター、副作用処理、および各言語（TypeScript / Go / Python）で即座に実行可能なスキャフォールドを必要とする場合
- トリガーキーワード：「レコメンドシステム」「フィードアルゴリズム」「ランキングパイプライン」「おすすめフィード」「候補パイプライン」「コンテンツ推薦」「推薦パイプライン設計」「RAG検索リランカー」

## 使用してはならないケース

- モデル自体のアーキテクチャ設計（Transformer設計、Two-Tower検索、埋め込み学習など）— 本スキルはモデルの*周辺配管（パイプライン）*を扱うものであり、モデルそのものではありません。
- 純粋な機械学習の学習パイプライン — スコアリング関数の学習はユーザーの責任範囲です。
- デプロイ済みパイプラインの実運用（監視、オートスケーリングなど）— スコープ外です。

## 6段階フレームワーク (The Six-Stage Framework)

| # | ステージ | 役割 | 並列実行 |
|---|---|---|---|
| 1 | **Source（生成）** | 1つまたは複数の起点から候補アイテムを取得する | 可 — 複数ソースを並列実行 |
| 2 | **Hydrator（補完）** | フィルタリングやスコアリングに必要なメタデータを各候補に付与する | 可 — 独立したハイドレーターを並列実行 |
| 3 | **Filter（除外）** | 表示すべきでない候補（ブロック、期限切れ、重複、対象外）を排除する | 直列 — 後のフィルターほど処理件数が減少 |
| 4 | **Scorer（採点）** | 残った候補に1つ以上のスコアを付与する | 直列 — 後のスコアラーが前のスコアを参照可能 |
| 5 | **Selector（選抜）** | 最終スコアでソートし、上位K件を抽出する | 単一処理 |
| 6 | **SideEffect（副作用）** | 配信IDのキャッシュ、インプレッション記録、イベント発行、カウンター更新 | 非同期 — レスポンスを絶対にブロックしない |

### なぜこの順序でなければならないのか

- **Hydrationの前にSource:** 候補アイテムが確定してから、初めてメタデータ補完のコストを支払うべきだからです。
- **Filteringの前にHydration:** 多くのフィルターは、Source段階では存在しないメタデータを必要とするからです。
- **Scoringの前にFiltering:** スコアリングは最も計算コストが高い処理です。対象外の候補を事前に落としておく必要があります。
- **単一スコアラーではなくScorerチェーン:** 実際のシステムは「MLスコアリング + 多様性リランキング + ビジネスルール」を合成して機能するからです。
- **Scoringの後にSelector:** スコアリングを決定論的かつキャッシュ可能な状態に保つためです。
- **SideEffectは最後かつ非同期:** 副作用の処理によってユーザーへの応答が遅延してはならないからです。

## 呼び出し時のワークフロー

以下の8つのステップで進行します：

1. **ユースケースの明確化**（1往復、3つの質問）: ランク付け対象のアイテムは何か？入力コンテキストは何か？使用言語/ランタイムは何か？
2. **候補ソースの特定**: 通常はネットワーク内（フォロー中、所有、購読） + ネットワーク外（ML検索、トレンド、類似アイテム）。
3. **必要なHydrationの洗い出し**: 各フィルターとスコアラーが、ソースから取得できないどのデータを必要としているか？
4. **フィルターの選定**: 重複除外、自分自身の除外、鮮度/期限、ブロック/ミュート、既読/配信済み除外、適格性。順序が重要（コストの低いものから順に適用）。
5. **スコアラーチェーンの設計**: プライマリ（ML） → コンバイナー（重み付き複数アクション） → 多様性制御 → ビジネスルール。
6. **Selectorの設計**: 最終スコアで降順ソートし、上位K件を取得（またはネットワーク内/外の層化配分）。
7. **SideEffectsの設計**: 配信IDのキャッシュ、インプレッションイベントの発行、カウンター更新、分析ログ記録（すべてfire-and-forget）。
8. **スキャフォールドの生成**: ユーザーの技術スタックに合わせた実装コードを生成。

## 提示すべき重要なトレードオフ（暗黙の前提にしない）

### 1. 単一スコア vs 複数アクション予測 (Multi-Action Prediction)
- **単一スコア**: 関連性を予測する1つのモデルを学習。挙動を変えるにはモデルの再学習が必要。
- **複数アクション**: 複数のアクション（閲覧、いいね、共有、スキップ、通報）の発生確率 `P(action)` を個別に予測し、配信時に重み付けして合算。挙動を変えるには重みパラメーターを変更するだけでよく、再学習は不要。
- *推奨:* 頻繁なチューニングが予想される場合は、複数アクション予測を推奨します。

### 2. スコアリングにおける候補の隔離 (Candidate Isolation)
- **隔離型 (Isolated)**: 各候補を独立してスコアリング。決定論的でキャッシュが容易。
- **結合型 (Joint)**: スコアリング時に候補同士が相互参照（例：バッチ全体のTransformer処理）。表現力は高いが、バッチ構成によって結果が非決定論的になる。
- *推奨:* 原則として隔離型をデフォルトとします。バッチ全体の多様性制御など明確な理由がある場合のみ結合型を採用します。

### 3. オンライン vs オフライン
- **リクエスト時（オンライン）**: リクエストごとにパイプラインを実行。許容レイテンシ：100〜300ms（デフォルト）。
- **事前計算（オフラインバッチ）**: 定期的にパイプラインを実行し結果をキャッシュ。低レイテンシだが鮮度は劣る。
- **ハイブリッド**: 候補抽出はオフライン、ランキングはオンラインで実行。

## 厳格なルール

1. **ベンチマーク数値を捏造しないこと。** 「どれくらい速くなりますか？」に対しては「ワークロードに依存するため、実測してください」と回答します。
2. **適切なクレジット表記。** 本パターンに言及する際は、「xAIのオープンソースFor Youアルゴリズム (`github.com/xai-org/x-algorithm`, Apache 2.0) により普及したパターン」と明記します。
3. **商標を使用しないこと。** ユーザーの成果物に「X風」や「For You」などの商標名を使用しないでください（「候補パイプライン」「フィードパイプライン」「ランキングパイプライン」などを推奨）。
4. **トレードオフを明示すること。** 単一 vs 複数アクション、隔離 vs 結合、オンライン vs オフラインを勝手に決め打たないでください。
5. **生成するスキャフォールドは実際に動作すること。** 動作しない疑似コードをコードとして提示してはなりません。
6. **フィルター順序の徹底。** 軽量なものを重いものより先に、全体共通のものをユーザー固有のものより先に適用します。
7. **副作用でレスポンスをブロックしないこと。** ゴルーチン、`await` なしのPromise、`asyncio` タスクなどのfire-and-forgetパターンで実装します。

## アンチパターン

- フィルタリングの前にスコアリングを行う（後で除外される候補に無駄な計算リソースを浪費する）。
- 同期的な副作用処理（キャッシュ書き込みやログ送信がユーザーへの応答をブロックする）。
- 複数の目的（エンゲージメント vs 安全性 vs 多様性 vs 広告）を調整する必要があるのに、単一の「関連度スコア」に頼る。
- 結合型スコアリングを安易にデフォルト化する（非決定論的になり、キャッシュが困難になる）。
- 「説明用」として実行できない疑似コードを生成する。
