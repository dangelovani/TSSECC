# Master Agreement Generator（マスター契約書ジェネレーター）

1つのマスターテンプレート、取引先ごとの1つの小さな仕様ファイル（Spec）、そして1回のドラフトビルドステップ。
ジェネレーターは、完成したテンプレートから生成された文書を含め、すべての出力を常に **DRAFT（下書き）** とラベル付けします。変換が成功したことは成果物が生成されたことを証明するだけであり、法的な完全性、契約締結権限、または送信・署名の準備が整っていることを意味するものではありません。締結済み契約書によっては、書面通知により対象取引を追加できる場合がありますが、その権限は別紙A（Schedule A）ワークフローを使用する前に確認されなければなりません。

## 使用場面

- 基本契約書（秘密保持契約（NDA）、紹介料・調達手数料契約、不正競争・迂回防止契約、マスターサービス契約など）を、同一の条項と一部の取引先固有の項目のみを変更して多数の取引先に発行するとき。
- 案件が継続的に追加され、その都度契約書を一から作成し直すことがボトルネックになっているとき。
- 文書がバージョン管理されたソースから再現可能であり、差分（diff）の確認が可能で、手作業による編集が排除されている必要があるとき。
- 署名欄が自動化によって配置されるため、安定したページレイアウトが必要なとき。

## 動作の仕組み

### テンプレート

`{{PLACEHOLDER}}` フィールドを含む単一の Markdown テンプレートです。取引先固有の値はすべてプレースホルダーとなり、それ以外の部分は固定テキストです。ひな形は [references/master-template.example.md](references/master-template.example.md) にあります。一般的な例文を、顧問弁護士等のレビューを受けた正式な条項に置き換えて使用します。

スクリプトが補完するプレースホルダー:

| プレースホルダー | ソース |
| --- | --- |
| `{{DATE}}` | `spec.date`（デフォルトは当日） |
| `{{CP_SHORT}}` | `spec.short`（取引先の略称） |
| `{{CP_LEGAL}}`, `{{CP_JURIS}}`, `{{CP_ADDR}}` | 仕様フィールド、または署名時に取引先が記入するための空欄 |
| `{{ROLE_CLAUSE}}`, `{{FEE_TITLE}}`, `{{FEE_CLAUSE}}` | ロールテーブルから `spec.role` に応じて選択 |
| `{{SCHEDULE_ROWS}}` | `spec.schedule`、または「署名時の登録なし」行 |
| `{{SUPPLEMENT_CLAUSE}}` | `spec.supplement`（末尾の区切り文字付き、または空） |
| `{{CP_SIGBLOCK}}`, `{{CP_SIGNER}}`, `{{CP_TITLE}}`, `{{CP_EMAIL}}` | 署名ブロックフィールド（未定の場合は空欄） |

### 仕様（Spec）

取引先ごとに1つの JSON ファイルを作成します:

```json
{
  "file": "AcmeSupplier",
  "short": "Acme",
  "role": "supplier",
  "legal": "Acme Compute Ltd",
  "juris": "England and Wales company",
  "addr": "1 Example Street, London",
  "signer": "A. Person",
  "title": "Director",
  "email": "signer@example.com",
  "schedule": [["1", "2026-09-01", "Lot A (16 nodes)", "introducer", "12 months", "standard"]],
  "supplement": "the Data Processing Addendum dated 2026-09-01"
}
```

ドラフト作成に必要なのは `file`、`short`、および `role` のみです。不足している署名欄は、レビューおよび後からの記入のために空行としてレンダリングされます。[references/spec.example.json](references/spec.example.json) を参照してください。

`file` はディレクトリ要素を含まない、`AcmeSupplier` などの移植性の高い空でないファイル名でなければなりません。パス区切り文字、ドライブ/UNC構文、制御文字、Windows予約文字/デバイス名、末尾のドットやスペースは拒否されます。無効な名前はサニタイズや自動変更されることなく、出力作成や Pandoc 呼び出しの前に拒否されます。

署名時に別紙Aへ記載する項目がない場合は、`schedule` を省略するか `[]` を指定します。指定する場合、スケジュールは「番号、日付、保護対象取引先またはロット、役割、条件、手数料」の順序で並んだ6セルの配列の密な配列でなければなりません。各セルは有効な Unicode 文字列または有限の数値です。意図的な空欄には空文字列を使用できます。null、真偽値、オブジェクト、入れ子の配列、セルの欠落、および非有限数は、成果物の書き込み前に拒否されます。

セルは Markdown や HTML ではなくプレーンテキストです。パイプ、バックスラッシュ、バッククォートなどの構文文字はエスケープされ、元のフィールドに保持されます。改行（CRLF、CR、LF）はスペースに変換されます。

### ロールテーブル

`spec.role` に応じて3つの文字列（基本取り決め条項、手数料セクションのタイトル、および手数料条項の冒頭文）が選択されます。

| ロール | 支払い元 | 条項の骨子 |
| --- | --- | --- |
| buyer（買い手） | 取引先が、紹介された相手方との取引に対して支払う | 取引先は、調達および紹介を行う非独占的権限を当社に付与する |
| supplier（サプライヤー） | 取引先が、紹介された相手方との取引に対して支払う。当社が当事者として購入する場合はスケジュール条件で契約 | 取引先は、当社および当社が紹介する買い手に対して計算能力（キャパシティ）を提供する |
| mutual（相互） | 相手方の紹介によって成約した側が支払う | 双方が紹介可能であり、成約した側の当事者が支払う |

未知のロールはビルド時に拒否されます。

### ビルド

運用者がレビューしたテンプレートと仕様のみを使用してください。Pandoc は参照されたローカルまたはリモートリソースを読み取ることができますが、本ジェネレーターはファイルシステムやネットワークアクセスをサンドボックス化しません。適切な制限が課された環境で変換を実行してください。

```sh
node skills/master-agreement-generator/scripts/build-agreement.js \
  skills/master-agreement-generator/references/master-template.example.md \
  specs/AcmeSupplier.json \
  out/
```

スクリプトはプレースホルダーを置換し、スケジュール表をレンダリングして、必須の DRAFT 表示を含む `out/<file> MASTER.md` を書き込みます。デフォルト（または `--require-docx` 付与時）では、空でない `.docx` 成果物を生成するために Pandoc のインストールが必要です。Pandoc が存在しない場合、変換に失敗した場合、または出力が空の場合は終了コード1が返されます。

Markdown のドラフトのみを生成する場合は、明示的に `--markdown-only` を使用します。このモードでは Pandoc の検出や呼び出しは一切行われず、e-signワークフロー用の DOCX は提供されません。結果には常に `documentStatus: 'draft'` が記録されます。Markdown の再ビルド時には既存の DOCX が削除され、古い成果物が最新出力と誤認されるのを防ぎます。

本スキルには「締結用原本（execution copy）モード」は存在しません。例示テンプレートには意図的に未解決の指示用括弧が含まれており、プレースホルダーを埋めただけでは法的な条項は完成しません。締結用文書を準備する前に、条項、当事者情報、権限ある署名者、商業条件、および正確な文書バージョンについて個別の法務レビューを受けてください。DOCX 変換が成功したとしても、アップロード、送信、署名が認可されたわけではありません（`esign-field-placement` の承認ワークフローを参照）。

### 署名ページのジオメトリ

テンプレートは本文の末尾に OpenXML 改ページを配置しており、互換性のある DOCX レンダラーで署名ブロックが確実に新しいページから始まるように設計されています:

````markdown
```{=openxml}
<w:p><w:r><w:br w:type="page"/></w:r></w:p>
```
````

署名ページの構造（自社ブロックの後に取引先ブロック、それぞれ By、Name、Title、Email、Date を配置）は一貫していますが、テキスト量、フォント、レンダラーによって改ページ位置が変わる可能性があります。フィールドを配置する前に、レビュー済みの実際の文書とそのページジオメトリを必ず検査してください（`esign-field-placement` スキル参照）。

### 別紙A（Schedule A）追記ワークフロー

締結済み契約書の実際の権限および通知要件に従います:

1. 案件の採算性や交渉戦略を**社内**の交渉/承認チャンネルでレビューします。契約内容を送信する前に社内のコミットメント承認を取得してください。取引先との共有チャンネルは社内チャンネルではありません。
2. 提案された案件、ロール、条件、手数料、および発効日が、契約書に明記された別紙Aの通知権限の範囲内であることを確認します。基本条件の変更や権限外の改定には正規の変更覚書（Amendment）手続きが必要であり、通知だけで勝手に例外を作ることはできません。
3. 締結済み契約書で承認された受取人および通知チャンネル向けに、承認済みの取引先固有の日付入り通知書を起草します。保護対象取引先またはロット、承認されたロール、商業条件、適用手数料を含めます。社内マージン、交渉戦略、他社の取引条件、システムトレース、社内起票通知は除外します。
4. 送信前に、正確な通知書を運用者承認用に起票します（`operator-approval-loop` 参照）。承認または発言権限が得られるまで、取引先チャンネルでは沈黙を維持します。
5. 契約書の要件に従って、正規の配信証拠、発効日、および異議申し立ての有無を記録します。締結済み文書は変更不可（イミュータブル）として保持し、追跡されているスケジュール記録を更新して、社内レビュー用の**統合ドラフトビュー（draft consolidated view）**を再ビルドします。この再ビルドは締結済み契約書を置き換えるものではなく、法的効力を証明するものでもありません。

## 具体例

### 通知テキストの例

参考用のドラフトです: 締結済み契約書が認可し、運用者がこの正確な通知内容を承認した場合にのみ使用してください。

```text
Schedule A notice, 2026-09-02
Agreement: Master Agreement dated 2026-08-14 between Us and Acme
Entry 2: Lot B, 8 nodes, region EU-West
Role: introducer
Terms: 6 month term, start no later than 2026-10-01
Fee: standard
This entry takes effect today unless you object within ten business days
with dated written evidence of a prior relationship with the counterparty.
```

### 仕様への項目の追加

```json
"schedule": [
  ["1", "2026-08-20", "Lot A (16 nodes)", "introducer", "12 months", "standard"],
  ["2", "2026-09-02", "Lot B (8 nodes, EU-West)", "introducer", "6 months", "standard"]
]
```

再ビルドし、Markdown の差分を確認した上で、変更されていない締結済み契約書および通知エビデンスとともに、統合ドラフトを社内記録に添付します。

### 署名時に取引先が自社情報を記入する場合

ドラフト作成時は、仕様から `legal`、`juris`、`addr`、`signer`、`title`、`email` を省略して空行をレンダリングします。個別にレビューされた締結ワークフローにおいて、取引先がどの項目を記入してよいかを決定し、実際のフィールドを検証する必要があります。
