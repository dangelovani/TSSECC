# チームエージェント・オーケストレーション (Team Agent Orchestration)

エージェントを単一のアシスタントではなくチームとして運用する場合に本スキルを使用します。作業項目の明確化、所有権の明示、エージェントかんばん（Kanban）の状態管理、ブランチ/ワークツリーの隔離、コントロールパネルの可視化、マージゲートの徹底を通じて、信頼性の高いチームオーケストレーションを実現します。

## 発動タイミング

- タスクが複数のエージェント、ツール、ハーネス、ブランチ、またはワークツリー（Git Worktree）にまたがる場合。
- ユーザーがチームオーケストレーション、エージェントかんばん、部隊（Squad）、コンダクター、コントロールパネル、マネージャー、デスクトップアプリ、Zellij、tmux、Hermes、Devin、Codex、Claude Code、マルチエージェント作業に言及した場合。
- プロジェクトにおいて、人間とエージェント間で共有されるワークフロー状態が必要な場合。
- 既存のエージェントの並列展開（Fan-out）が成果物を生成しているものの、マージ可能なプロダクトとして統合できていない場合。

## 運用モデル

各エージェントを、明確な規約を持つ「チームメンバー」として扱います：

- **所有者 (Owner)**: その作業項目に責任を持つ人間またはエージェント。
- **スコープ (Scope)**: 変更対象ファイル、ブランチ、使用ツール、および禁止領域。
- **状態 (State)**: Backlog, Ready, Running, Review, Blocked, Merged, Archived。
- **エビデンス (Evidence)**: テスト結果、スクリーンショット、ログ、レビューノート、評価レポート。
- **マージゲート (Merge gate)**: メインラインへの統合を許可する厳密な条件。

## エージェントかんばん (Agent Kanban)

セッションをまたいで作業状況を可視化・共有する必要がある場合にかんばんを使用します。

| カラム | 意味 | 完了基準（Exit Criteria） |
| --- | --- | --- |
| **Backlog** | 候補作業項目、未具体化 | 受入条件（Acceptance criteria）が記述されている |
| **Ready** | 具体化済み、アサイン可能 | 所有者およびブランチ/ワークツリーが割り当てられている |
| **Running** | エージェントが作業中 | ハンドオフ成果物および変更ファイルが存在する |
| **Review** | 作業完了、未マージ | テスト、差分レビュー、リスクチェックを通過している |
| **Blocked** | 外部入力待ちまたはゲート不通過 | ブロッカーの所有者と次のアクションが明確である |
| **Merged** | メインラインへ統合済み | PRがマージされたかローカルのmainが更新されている |
| **Archived** | 対応不要・アーカイブ | その理由が記録されている |

各カードは以下のスキーマに準拠します：

```json
{
  "id": "agent-card-001",
  "title": "動的ワークフロースキルの構築",
  "owner": "codex",
  "state": "running",
  "branch": "product/dynamic-workflow-team-orchestration",
  "worktree": ".",
  "acceptance": [
    "スキルが存在すること",
    "テストが必要な概念を網羅していること",
    "コンテンツ成果物に動画および記事の切り口が含まれていること"
  ],
  "merge_gate": "リント、フォーカステスト、カタログ検査の全通過",
  "handoff": "path/to/handoff.md"
}
```

## チームオーケストレーションの流れ

1. **ボードの具体化:** 曖昧な要求を、所有者とマージゲートが定義された作業項目へと変換する。
2. **実行モードの選定:** 単一エージェント、動的ワークフローモード、dmux/tmux、Git Worktree展開、または外部デスクトップオーケストレーターを選択。
3. **境界の割り当て:** カードごとに1つの所有者を定め、ファイルスコープを明確にし、インテグレーター（統合担当）なしでの競合書き込みを排除する。
4. **エージェントの稼働:** 各エージェントは単にコードを書くだけでなく、エビデンスとハンドオフノートを作成する。
5. **段階的レビュー:** テスト通過 → 差分レビュー → セキュリティ/リスク検証 → コンテンツ/品質の洗練。
6. **計画的マージ:** 1人のインテグレーターがコンフリクトを解決し、コントロールパネルやステータス成果物を更新する。
7. **再利用可能スキルの抽出:** カードの作業パターンが反復する場合は、それを `skills/` へと昇格させる。

## コントロールパネルの要件

チームオーケストレーション用のコントロールパネルは以下を表示する必要があります：

- アクティブな作業項目と各エージェントのかんばん状態
- 所有者、ハーネス名、ブランチ、ワークツリー、最終ハートビート
- ハンドオフ成果物、テスト、スクリーンショット、PRへのリンク
- 所有者および解消アクションごとにグループ化されたブロッカー
- 感覚ではなくゲート基準に基づくマージ準備状況
- 共通スキルとして昇格すべき再利用可能ワークフロー候補

「誰が所有しているか」「何が変更されたか」「どのゲートが失敗したか」「何を安全にマージできるか」に答えられない状態で、自動化を過剰に追加してはなりません。

## 動的ワークフローとの互換性

カードが動的ワークフローモードを必要とする場合：

- タスクローカルなハーネスをカードの所有者配下に配置する。
- 入力と出力をカード上に記録する。
- RunningからReviewへ移行する前に評価（Eval）を必須とする。
- 繰り返し使用された後にのみ、ハーネスを共通スキルへと昇格させる。

## 警戒すべき失敗パターン

- **エージェントの無秩序化（Agent soup）:** 多数のエージェントが無計画に稼働し、所有者もマージゲートも存在しない。
- **不可視の作業:** 有用な成果物がチャット履歴の中にしか存在しない。
- **形骸化したかんばん:** かんばんボードは存在するが、カードに受入条件が書かれていない。
- **書き込みの重複衝突:** 並列エージェントがWorktreeを使わずに同一ファイルを編集してしまう。
- **プロダクト成果物の欠如:** ドキュメントばかり生成され、実行可能・公開可能な成果物が生まれない。

## 出力基準（Output Standard）

各オーケストレーションパスの完了時に以下を提示します：

- ボード/カードの更新内容
- マージ済みまたは保留中のブランチ
- テストおよび評価エビデンス
- 所有者と次回アクションが明記されたブロッカー
- 新たな共通スキル候補
