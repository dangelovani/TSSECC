# Contract-First Collaboration（契約ファーストの協調開発）

単一の信頼できる機械検証可能な契約（コントラクト）を通じて、フロントエンド/バックエンド間やサービス間の開発を調整します。利用側（コンシューマー）が必要な形状を宣言し、提供側（プロバイダー）がその形状を実装し、双方が統合前に同一の成果物に対して検証を行います。

本スキルはチームがシステムの境界をどのように変更すべきかを統括します。優れたAPIの設計を扱う `api-design` や、修正済みバグの再発を防止する `ai-regression-testing` を補完するものです。

## 有効化のタイミング

- フロントエンドとバックエンドの開発が並行して進められるとき。
- 2つ以上のサービス間でAPIペイロード、イベント、またはコマンドを交換するとき。
- フィールド名、null許容性、enum定義、またはエラーの形式が頻繁に乖離（ドリフト）するとき。
- プロバイダーがタスク指向のレスポンスではなくストレージモデルをそのまま露出しているため、コンシューマーが複数のAPI呼び出しを余儀なくされているとき。
- プロバイダーの変更によって、別の担当者やエージェントが保守しているコンシューマーが破損するリスクがあるとき。
- モックのレスポンスと本番のレスポンスの形式が一致しなくなったとき。

単一のコミットでアトミックに変更が完結し、独立したコンシューマーが存在しない単一モジュール内の境界にまで重厚な契約機構を導入する必要はありません（共有の型定義で十分です）。

## 境界成果物（The Boundary Artifact）

各境界に対して、バージョン管理された単一の公式成果物を選定します:

- HTTP API には **OpenAPI**
- イベント駆動型 API には **AsyncAPI**
- RPC またはメッセージスキーマには **Protocol Buffers**
- スタンドアロンのペイロードには **JSON Schema**
- すべての関係者が同一のビルドおよびランタイム互換性モデルを共有している場合に限り、型付きインターフェース（TypeScript等）

ファイル名自体は重要ではありません。「権威（唯一の真実）」であるかどうかが重要です。同じペイロード定義を、Wiki、テキスト仕様書、モックファイル、プロバイダーのコードに個別に分散して二重管理してはなりません。

成果物は、コンシューマーが依存する以下の観察可能な振る舞いを定義する必要があります:

- オペレーション名またはイベント名
- リクエストおよびレスポンスの形状
- 必須フィールドと任意フィールド
- null許容性（nullable）およびデフォルト値
- enum（列挙型）の値
- エラーレスポンス
- 互換性またはバージョニングのルール

実装の詳細を混入させてはなりません。データベースのカラム名、内部クラス、クエリ実行計画などは、コンシューマーから直接観測できない限り契約の一部ではありません。

## コンシューマーファーストのワークフロー

### 1. 利用者（コンシューマー）と責任者の特定

以下を記録します:
- 誰がこの境界を利用（消費）するか
- 誰がプロバイダーを所有（保守）するか
- 誰が契約の変更を承認できるか
- どの成果物が唯一の真実（authoritative）か

### 2. コンシューマーの業務（ジョブ）の記述

各コンシューマーが何を描画・達成すべきかを出発点とします。以下を問いかけます:
- 実際に必須となるフィールドはどれか？
- 欠落（未指定）、空（empty）、null はそれぞれ何を意味するか？
- どのIDを文字列（string）として保持すべきか？（数値化による丸め誤差防止）
- コンシューマーが処理可能なenum値はどれか？
- タスク指向の1つのレスポンスで、密結合した複数の呼び出しを置き換えられないか？
- どのようなエラーに対してコンシューマー側で分岐処理が必要か？

データベースの行をそのまま露出し、それを契約と呼んではいけません。

### 3. 必要最小限の有用な契約の定義

例:

```yaml
# openapi.yaml
openapi: 3.1.0
components:
  schemas:
    OrderSummary:
      type: object
      required: [id, status, total]
      properties:
        id:
          type: string
          description: 不透明な識別子。決して数値としてパースしないこと。
        status:
          type: string
          enum: [pending, paid, cancelled]
        total:
          type: number
          format: double
          minimum: 0
        cancellationReason:
          type: [string, "null"]
```

構文だけでなくセマンティクス（意味的な制約）も定義します。例えば、「`status` が `cancelled` 以外のときは `cancellationReason` は必ず null になる」といったルールを文書化します。

### 4. コンシューマーの型の自動生成または導出

手作業でのコピーではなく、自動生成された型定義を優先します:

```bash
npm run generate:api-types
```

```typescript
import type { components } from "./generated/api";

type OrderSummary = components["schemas"]["OrderSummary"];

export const paidOrderMock = {
  id: "9007199254740993123",
  status: "paid",
  total: 49.9,
  cancellationReason: null,
} satisfies OrderSummary;
```

プロバイダーの実装が進んでいる間でも、コンシューマーは契約に準拠したモックを相手に開発を進めることができます。

### 5. プロバイダーの実装と検証

プロバイダーは、実際のレスポンスが同一の契約成果物を満たしていることを証明しなければなりません:

```typescript
import type { components } from "./generated/api";

type OrderSummary = components["schemas"]["OrderSummary"];

export function toOrderSummary(row: OrderRow): OrderSummary {
  return {
    // データベースから取得したIDは、JavaScriptの数値に丸められる前に
    // 最初から string または bigint として扱う必要がある。
    id: String(row.id),
    status: row.status,
    total: row.total,
    cancellationReason: row.cancellation_reason,
  };
}
```

静的型チェックだけでなく、シリアライズ境界における実行時スキーマ検証やフレームワークレベルの契約テストを追加してください。

### 6. エビデンス比較による統合

マージ前のチェック事項:
- コンシューマーの型が正常に自動生成できること
- コンシューマー側のフィクスチャが契約に準拠していること
- プロバイダーのレスポンスが契約に準拠していること
- 少なくとも1つのエンドツーエンドの正常系が動作すること
- 未文書化のフィールドに依存しているコンシューマーが存在しないこと

統合における問いは「双方が各自の単体テストに合格したか？」ではなく、「**双方が同一の境界成果物に対して適合しているか？**」です。

## 契約変更プロトコル

**決して実装を先に変更し、後から契約を更新してはなりません。**

1. コンシューマーの要求と互換性への影響を提案する。
2. 公式の契約成果物を変更する。
3. 影響を受けるコンシューマーおよびプロバイダーと契約の差分（diff）をレビューする。
4. 型、クライアントコード、またはフィクスチャを再生成する。
5. プロバイダーおよびコンシューマーの実装を更新する。
6. 双方が検証テストを実行する。
7. すべての関係者が新しい契約に合意した後にのみマージする。

後方互換性のある追加変更の場合は、古いコンシューマーが引き続き動作することを確認します。破壊的変更の場合は、既存のフィールドを勝手に再定義するのではなく、リポジトリのバージョニングまたは移行ポリシーに従ってください。

## アンチパターン

- **プロバイダー都合の当て推量:** DBのテーブル定義（`select *`）がそのまま公開APIに漏洩し、コンシューマーが求めていない内部変更で障害が発生する。
- **信頼できる情報源の多重化:** Wiki、フロントエンド型、バックエンドシリアライザー、モックJSONが各自で保守され、どれが正しいか分からなくなる。
- **コンパイル時の型のみを過信:** `as unknown as OrderSummary` のようなキャストによって、実行時の非互換なデータ構造が隠蔽されてしまう。
- **無断でのフィールド変更:** 契約の改定やレビューを経ずに、コード側だけでフィールド名を変更してしまう。
- **事後的な契約作成:** 双方が実装を終えた後に契約書を作成すること（並行開発の調整にならず、乖離を防げない）。

## チェックリスト

- [ ] コンシューマーおよびプロバイダーの責任者が明確である。
- [ ] 唯一の公式な契約成果物が特定されている。
- [ ] 必須フィールド、null許容性、enum、エラーが明示されている。
- [ ] コンシューマーの型やフィクスチャが契約から自動生成されている。
- [ ] プロバイダーのレスポンスが契約と照合して検証されている。
- [ ] サンドボックス、エラー、条件付きパスが網羅されている。
- [ ] 破壊的変更に対する移行/バージョニング計画がある。
- [ ] 統合前に双方が同一の契約に対して検証をパスしている。
