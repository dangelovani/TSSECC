# Agent Self-Evaluation（エージェント自己評価）

複雑なタスクを完了した後、エージェントは一旦立ち止まり、構造化された5軸のルーブリックに照らして自身の出力を評価します。これは合否判定のゲートではありません — 見落としを捉え、過信に注意を促し、ユーザーに指摘される前に改善ポイントを浮き彫りにするための意図的な内省ステップです。

## 有効化のタイミング

- 3ファイル以上または50行以上のコードを書いた後
- マルチステップのワークフロー（実装 → テスト → レビュー）を完了した後
- 3回以上の試行を要したデバッグセッションの後
- 設計ドキュメント、アーキテクチャ決定記録、または文書分析を作成した後
- ユーザーから「今の出来はどうだった？」「自己採点して」と尋ねられたとき
- セッション終了時のStopフック（設定されている場合 — `references/hook-integration.md` を参照）

## コアコンセプト

### 5つの評価軸

| 評価軸 | 問い | 何を検出するか |
|---|---|---|
| **正確性（Accuracy）** | 事実、主張、および出力は正しいか？ | ハルシネーション、誤ったAPI名、構文エラー、虚偽の記述 |
| **完全性（Completeness）** | ユーザーが求めたすべてを網羅しているか？ | 見落としたエッジケース、未処理のエラーパス、忘れられた要件、スキップされたサブタスク |
| **明確性（Clarity）** | 説明は分かりやすく、構造化されているか？ | 混乱を招く説明、定義のない専門用語、文脈の欠落、冗長な語り口 |
| **実行可能性（Actionability）** | ユーザーが出力に基づいて即座に行動できるか？ | 曖昧な提案、欠落した手順、具体的な方法を示さない「〜すべき」、検証パスの欠落 |
| **簡潔性（Conciseness）** | 必要最小限の単語/トークン数で表現されているか？ | 重複、過剰な説明、ユーザーの質問の不必要な反復、無駄な埋め草 |

### スコアリング尺度

```
5 — 卓越（Exceptional）: 合理的な改善の余地がない
4 — 良好（Good）: 軽微な指摘のみで、実質的な欠落はない
3 — 合格点（Adequate）: 要求は満たしているが、少なくとも1つの軸に目立つ弱点がある
2 — 脆弱（Weak）: ユーザビリティや正確性に影響を与える明確な欠落がある
1 — 不良（Poor）: 要求を根本的に外しているか、重大なエラーを含んでいる
```

### 根拠提示の原則（The Evidence Rule）

5点未満のすべてのスコアには、必ず具体的な根拠（エビデンス）を引用しなければなりません。3点のスコアに対して単に「もっと良くできた」とだけ書くことは許されません — 何が欠落しているか、または何が間違っているかを正確に述べる必要があります。基本原則は **「名前を挙げるだけでなく、ギャップそのものを示せ（Show the gap, don't just name it.）」** です。

## ワークフロー

### ステップ 1: 生の材料の収集

評価対象となる情報を集めます:

```
- ユーザーの元の要求（会話履歴の再確認）
- 自身の最終回答/出力（成果物）
- 正確性を検証するツールの出力（テスト結果、終了コード、リント出力）
- タスク中に受け取ったユーザーからのフィードバック（修正指示、「やり直して」「それは違う」など）
```

### ステップ 2: 各軸の独立したスコアリング

5つの軸を1つずつ評価します。各軸について:

1. 評価軸の問いを読む
2. 出力の中から根拠（または根拠の欠如）を見つける
3. 1〜5点のスコアを付与する
4. スコアが5未満の場合、そのギャップを引用した1文の改善メモを書く

頭の中で先に平均スコアを決めてから逆算してはいけません。それぞれの軸を新鮮な目で評価してください。

### ステップ 3: 評価レポートの作成

`templates/evaluation-report.md` のテンプレートを使用します。レポートには以下を含める必要があります:

```
- 1行サマリー
- 5軸スコアカード（軸ごとのスコアと根拠）
- 総合スコア（単純平均、小数点第1位に四捨五入）
- 影響度順にランク付けされた1〜3件の具体的改善点
- セルフチェック: 「ユーザーはこの評価に同意するか？」
```

### ステップ 4: 改善の適用

いずれかの軸が3点以下となった場合:

1. 何をどのように変えるかを表明する
2. そのギャップが30秒未満で修正可能な場合（欠落したリンク、不鮮明な表現など）、直ちに修正する
3. 手戻りや再作業が必要な場合は、明示的にフラグを立てる: 「この軸は [根拠] のため [理由] と評価されました。[具体的な修正] を適用して再実行すれば、おそらく [スコア] まで向上します。」

## コード例

### 例: 良好な評価（スコア 4以上）

```
タスク: HTTPクライアントにリトライロジックを追加

スコアカード:
  正確性:      5 — すべてのAPI呼び出しが正確。検証済み: リトライは指数バックオフを使用。
                  ハルシネーションによるメソッド呼び出しなし。
  完全性:      4 — 正常系＋3つのエラーケースを網羅。欠落: 接続ハング時のタイムアウト処理。
  明確性:      5 — コードコメントでバックオフ計算式を説明。PR説明に契機となったインシデントへのリンクを記載。
  実行可能性:  5 — 単一のマージで完結。フォローアップタスク不要。テスト合格。
  簡潔性:      4 — 合計47行。リトライループをヘルパーに抽出すれば約8行削減可能。

総合: 4.6 — 1点のギャップ（タイムアウト処理）。マージ前に修正すること。
```

### 例: 脆弱な評価（スコア 2〜3）

```
タスク: HTTPクライアントにリトライロジックを追加

スコアカード:
  正確性:      2 — httpxベースのコードベースに対してurllib3を使用。誤ったライブラリの採用。
  完全性:      3 — GETでは機能するが、POST/PUTが未処理（ユーザーは「すべてのHTTPリクエスト」と指定）。
  明確性:      4 — コードの可読性は良好。適切な変数名。
  実行可能性:  2 — 「テストを追加」と記載されているがテストファイルが作成されていない。
                  ユーザーがマージ前にテストを書く必要がある。
  簡潔性:      3 — 120行。共有のRetryConfigオブジェクトを使用せず、リトライ設定が3箇所に重複。

総合: 2.8 — 誤ったライブラリを使用。httpxへの書き直しが必要。
  まず正確性を修正（httpxへ切り替え）、次にすべてのHTTPメソッドへ拡張し、その後に設定を集約する。
```

## アンチパターン

### 「すべてが5点」

```
FAIL: 正確性:   5 — すべて良好。
      完全性:   5 — すべて網羅。
      明確性:   5 — 明確。
```

具体的な根拠が挙げられていません。これは自己満足であり、評価ではありません。真の5点を付けるには、改善の余地が一切ないことを証明する必要があります。

### スコープ外の事柄による過剰な減点

```
FAIL: 完全性: 2 — WebSocket接続やgRPCストリーミングに対応していない
      （ユーザーはこれらを一切求めていない）
```

自分が追加で構築できたかもしれないものではなく、ユーザーが実際に要求した内容に対してのみ評価を行ってください。

### 過去の議論の蒸し返し

```
FAIL: 「前にも述べたように、このアプローチは間違っている。スコア: 1」
```

評価は納品された成果物に対するものであり、すでに決定された設計判断を蒸し返すためのものではありません。アプローチが間違っていたのであれば、納品前に指摘されるべきでした。

### 個人の好みと客観的なギャップの混同

```
FAIL: 「スコア: 3。Pythonのデコレータが好きではないため。」
```

「好きではない」は根拠になりません。可読性、テスト容易性、または正確性に関する具体的な懸念を挙げるか、さもなければスコアを4以上に保ってください。

## ベストプラクティス

- **プロセスではなく成果物を評価する。** ユーザーが気にするのは何が提供されたかであり、何回試行錯誤したかではありません。
- **弱い軸ごとに1つの改善点に絞る。** 1つの軸に5つも並べるのではなく、最も影響の大きいギャップを選びます。
- **改善点をユーザーへの影響に結びつける。** 「エラー処理を追加する」よりも、「エラー処理の欠落により、ユーザーのAPI呼び出しが無言でクラッシュする」の方が優れています。
- **「修正された状態」を具体的に定義する。** 「ライブラリの問題を修正する」よりも、「リトライが設定されたhttpxトランスポートで再実行する」の方が具体的です。
- **ツールの出力を根拠として活用する。** テストが通過したならそれを引用し、リントがクリーンならそれを引用します。推測するのではなく、grep等で証明を探してください。
- **ギャップが見つからないときは、より深く掘り下げる。** 5軸すべてで完璧なスコアが出ることは極めて稀です。「もし自分がユーザーだったら、この出力のどこにストレスを感じるだろうか？」と自問してください。
