# レイテンシ重視システム (Latency Critical Systems)

リアルタイム処理、ホットパス、ストリーミングの鮮度、または処理速度が重要なシステムを扱う場合に本スキルを使用します。高頻度取引（HFT）ライクなインフラも対象に含まれますが、本スキルはエンジニアリングに特化しており、実際の取引の認可や投資助言を提供するものではありません。

## 指標の分解・個別計測

すべてを単に「速い」の一言で片付けてはなりません。以下の指標を個別に追跡します：

- p50, p95, p99 レイテンシ
- スループット（Throughput）
- データ鮮度・遅延時間（Freshness age）
- キューの滞留深度（Queue depth）
- キャッシュヒット率
- プロバイダ/外部APIの応答時間
- ブラウザの描画時間（Render time）
- 負荷環境下での正当性
- 障害発生時および再試行時の挙動

## ホットパスのマッピング

ユーザーやイベントの発生から、最終的な可視状態に至るまでの経路を可視化します：

```text
発生イベント -> プロバイダAPI -> 取り込みワーカー -> キュー -> キャッシュ -> エッジルート
-> クライアントストリーム -> ブラウザ描画 -> ユーザーが視認する状態
```

その上で、各セグメントの所要時間を個別に計測します。

## 最適化の優先順位

1. 不要なネットワーク往復（ラウンドトリップ）を排除する。
2. 安定した読み取りデータを鮮度メタデータ付きでキャッシュする。
3. 小さなAPI呼び出しやDB書き込みをバッチ化する。
4. コンピュート処理をデータやユーザーの近く（エッジ等）へ移動する。
5. ホットパス（高頻度）とコールドパス（低頻度）を分離する。
6. キューが無制限に肥大化する前にバックプレッシャー（背圧制御）を適用する。
7. 鮮度やUXの改善につながる場合にのみストリーミングを採用する。
8. データの陳腐化、プロバイダの性能劣化、キャッシュ異常を検知するカナリア監視を導入する。

## 検証手法

デプロイ済みの環境が存在する場合は、実際の読み戻し検証を行います：

- HTTPタイミングおよびレスポンスヘッダー
- プロバイダのデータ鮮度タイムスタンプ
- キューまたは非同期ジョブの状態
- エッジ/キャッシュのヒット状態
- 実際のUIの鮮度をブラウザで検証
- 再試行や縮退運転（Degraded mode）に関するログ

市場データや執行関連のパスの場合は、準備完了と判断する前に、板情報（Orderbook）の鮮度、VWAPの前提条件、プロバイダの稼働状態、キルスイッチ（強制遮断機構）の挙動も検証します。

## ガードレール

- 必須のバリデーションを省略してレイテンシを向上させてはならない。
- 高速なキャッシュヒットの陰に陳腐化した古いデータを隠蔽してはならない。
- 実測に基づかないクライアント側のラベルだけで「ミリ秒級」を謳ってはならない。
- 明示的な承認ゲートなしに、本番注文、破壊的マイグレーション、顧客影響のあるデプロイを実行してはならない。
- ログやベンチマークの成果物にシークレットや機密ペイロードを含めてはならない。
