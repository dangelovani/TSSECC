# ブランドディスカバリー (Brand Discovery)

構造化され、かつ適応的なブランドアイデンティティのインタビューを実施するために本スキルを使用します。最終ゴールは、組織がデザイナー、ライター、外部パートナーへのブリーフィングに活用できるマスターブランドブック（`90_SYNTHESIS.md`）を完成させることです。

このインタビューは複数セッションにわたって実施されます。会話が途切れても得られた知見が失われず、後続のセッションで中断箇所から正確に再開できるよう、回答は逐次ディスクに永続化保存します。

## 発動タイミング

- ブランドを新規立ち上げ、リポジショニングする際、または外部パートナーへ共有するための明文化されたアイデンティティ基準が必要な場合。
- 複数セッションにわたる進行が想定される場合（数日〜数週間にわたる対話）。
- 統合セッションを行う前に、複数の創業者やステークホルダーに個別のインタビューを実施する必要がある場合。
- 単なる雑談ではなく、構造化され再現性のある方法論を求めている場合。
- 既存のブランド情報が散散としており、暗黙知や特定創業者の頭の中にのみ存在しているため、明文化が必要な場合。

## セッション開始プロトコル

本スキルが呼び出されるたびに、質問を開始する**前に**必ず以下のステップを実行します：

1. **過去の進捗を確認する:** プロジェクトのブランドディレクトリ内に既存のモジュールファイル群および `state.json` チェックポイントが存在するか確認します。存在しない場合は新規開始とし、ブランド名、参加者、保存先パスを確認した上で第1モジュールから開始します。
2. **進行中モジュールファイルの確認:** 進行中のモジュールがある場合はそのファイルを読み込み、`## Raw` セクションに以前記録された回答を確認します。
3. **ユーザーへの状況報告:** 現在どのモジュールにいるか、その状態、残りの作業を2〜3文で簡潔に報告します。その上で「このまま続けますか？それとも別のモジュールに切り替えますか？」と確認します。

## インタビューの規律

すべてのモジュールで以下の原則を徹底します：

1. **質問は一度に1問のみ:** 質問の箇条書きリストを一度に提示してはなりません。
2. **各回答に対する対応:** 簡潔なパラフレーズ（要約） → 1つの深掘り質問、または話題が飽和した場合はそのスレッドを終了。沈黙のまま次の質問へ進んではなりません。
3. **ラダリング (Laddering):** すべての「何を（What）」という回答に対して、本質的なコアバリューが浮かび上がるまで「なぜそれがあなたにとって重要ですか？」と深掘りします（通常2〜4回反復）。
4. **なぜなぜ分析 (5 Whys):** 信念やポジショニングの主張に対して、表面的な宣言ではなく根本的な動機が表に出るまで「なぜ」を重ねます。
5. **浅い回答の検知:** 一般的、専門用語過多、または曖昧な回答に対しては、具体的な事例、顧客のエピソード、または数値を求めます。
6. **投射技法 (Projective Techniques)**（思考が膠着した際に各モジュールで1回使用）:
   - 「もしこのブランドが一人の人間だとしたら、どのように部屋に入ってきますか？」
   - ブランドの死亡記事（Obituary）:「もし組織が5年後に解散したとしたら、顧客は何を惜しみますか？ 伝えられなかったことで何を後悔しますか？」
   - 競合との対比:「称賛しているが、決してそのようにはなりたくない同業他社を1社挙げてください。具体的に何が間違ったモデルだと感じますか？」
7. **飽和シグナル (Saturation):** 2回連続で新しい情報が得られなくなった時点で、要約してそのモジュールをクローズします。
8. **モジュールの終了処理:** 以下の2つのセクションを持つ構造化モジュールファイルを書き出します：
   - `## Raw` — 発言の引用や具体例。
   - `## Synthesis` — 解釈、3つの候補表現、未解決の論点、参加者間の矛盾。
   その後、`state.json` チェックポイントを更新します。

## モジュールの順序

| ファイル名 | モジュール名 | 使用フレームワーク |
|---|---|---|
| `10_purpose-why.md` | パーパス / なぜ存在するのか | Sinek ゴールデンサークル、Lencioni |
| `20_positioning.md` | ポジショニング | Dunford「Obviously Awesome」、Moore テンプレート |
| `30_audience-niche.md` | オーディエンス &amp; ニッチ | Baker「専門性のビジネス」、ICP（理想顧客像） |
| `40_personality-archetype.md` | パーソナリティ &amp; アーキタイプ | Mark &amp; Pearson 12のアーキタイプ、Aaker 5次元 |
| `50_voice-tone.md` | ボイス &amp; トーン | ブランドボイスガイドライン |
| `60_narrative-story.md` | ナラティブ / ストーリー | Neumeier トゥルーライン、ブランドストーリーアーク |
| `70_founder-tension.md` | 創業者とスタジオブランドの緊張関係 | Enns「Win Without Pitching」 |
| `90_SYNTHESIS.md` | マスターブランドブック | Kapferer プリズム、Aaker ブランドシステム |

原則として順番通りに進めます。ユーザーが特定モジュールへのスキップを求めた場合はそれを尊重し、`state.json` に記録します。

## 状態記録プロトコル (State Write Protocol)

各モジュールが飽和または完了に達したら、以下の2つのファイルを書き出します：

1. **モジュールファイル** (`modules/{moduleFile}`): 完全なRawおよびSynthesisの内容。
2. **`state.json`**: 後続セッションで再開するための軽量チェックポイント。
   `completedModules`, `inProgressModule`, `nextModule`, `lastUpdated` を更新します。

スキーマ：
```json
{
  "session": "{brand_name}-brand-{YYYY-MM}",
  "outputPath": "{path_to_brand_identity_directory}",
  "completedModules": [],
  "inProgressModule": "10_purpose-why.md",
  "nextModule": "20_positioning.md",
  "participants": ["founder-A"],
  "lastUpdated": "{ISO-8601}"
}
```

書き込み後、「モジュールXを保存し状態を更新しました。次はYです」とユーザーに報告します。

**最終モジュール (90_SYNTHESIS.md):** 最終統合の執筆時、`state.json` の `inProgressModule` を `"90_SYNTHESIS.md"`、`nextModule` を `null` に設定します。書き込み完了後、`completedModules` に `"90_SYNTHESIS.md"` を追加し、`inProgressModule` を `null` に戻します。「ブランドブックが完成し、すべてのモジュールが保存されました」と報告します。

## 複数創業者モード (Multi-Founder Mode)

複数の創業者が参加する場合、共通モジュールファイルではなく各創業者の回答を `founders/{participant}.md` に個別に記録します。全員がモジュールを完了した後、統合（Reconciliation）パスを実行します：一致点と相違点をモジュールファイルにまとめ、全体アライメントワークショップのための「建設的な緊張関係」としてフラグを立てます。

## アンチパターン

- **状態を確認せずに開始すること:** 必ず既存のモジュールファイルや `state.json` の確認から開始してください。これを怠ると過去セッションの文脈が失われます。
- **複数の質問を一度に浴びせること:** 箇条書きの質問はチェックリスト的な浅い回答しか生みません。
- **飽和する前に勝手にSynthesisに進むこと:** 直近2問で新しい情報が出なくなるまで、モジュールを完了とみなしてはなりません。
- **複数創業者の統合ステップを省くこと:** 複数人が関わる場合、集団で最初から議論させるとアンカー効果（声の大きい人の意見への同調）が生じます。個別インタビューを終えてから統合します。
- **1回限りのセッションとして急いで終わらせること:** 本スキルは複数セッション向けに設計されています。1回の会話で無理に `90_SYNTHESIS.md` まで急ぐと薄っぺらい成果物になります。
